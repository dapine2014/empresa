## Comandos

Trabajar siempre dentro de `app/`. No hay Maven wrapper; se usa `mvn` del sistema. El build fija el bytecode a Java 21 (`--release 21` vía `<java.version>`), así que compila con cualquier JDK ≥ 21 aunque sea más nuevo; `maven-enforcer-plugin` corta el build en `validate` si el JDK es < 21 o Maven < 3.9.

```bash
cd app
mvn package                       # compila + empaqueta el jar (target/company-core-0.1.0-SNAPSHOT.jar)
mvn -DskipTests package           # empaqueta sin tests
mvn test                          # ejecuta la suite unitaria
mvn test -Dtest=MiClase#miMetodo  # ejecuta un único test
mvn spring-boot:run               # arranca el servicio en local (puerto 8081)
```

No hay tooling de lint configurado. La suite unitaria está en `src/test/java` y
cubre la validación de resultados de agentes, el inicio de misiones y el
enrutamiento del chat del CEO. Las integraciones con Neo4j, Kafka y Ollama se
mantienen fuera de estas pruebas para que no dependan de Docker.

Healthcheck: `GET http://localhost:8081/actuator/health` (actuator en el classpath; solo se exponen `health`, `info` y `metrics`, con probes de readiness/liveness activadas).

**Frontend** (`app/frontend/`, SPA React+Vite+TS — ver "Command Center web" más abajo):

```bash
cd app/frontend
npm install
npm run dev      # dev server en :5173, con proxy a :8081 (vite.config.ts) — no requiere Docker
npm run build    # compila a dist/, lo que copia el Dockerfile a src/main/resources/static
```

`mvn spring-boot:run` en local **no** compila ni sirve la SPA (no hay `frontend-maven-plugin`, deliberado — ver "Command Center web"): para probar el backend+frontend juntos como en producción, usar Docker; para desarrollar el frontend, `npm run dev` aparte apuntando al backend real en 8081.

Docker (la imagen construye con Maven **y** con Node en multi-stage — 3 stages: `frontend-build` (Node, compila la SPA) → `build` (Maven, empaqueta el jar con la SPA ya copiada a `src/main/resources/static`) → runtime `jre`):

```bash
docker network create ai-company-net   # red externa requerida (una sola vez)
docker compose build
docker compose up
```

`docker-compose.yml` **solo** define `company-core`. Neo4j, Ollama y Kafka se esperan ya en ejecución y accesibles, todos en la red `ai-company-net`; `docker-compose.yml` fija `KAFKA_BOOTSTRAP_SERVERS=storm-kafka:19092` (listener interno agregado a Kafka para `company-core`, ver `status.md` §9-10 y `EMPRESA_AI_TODO.md` §4.4). El default de `application.yml` para Kafka (`host.docker.internal:9092`) es el legado previo a ese listener y solo aplica si corres `mvn spring-boot:run` en local sin exportar `KAFKA_BOOTSTRAP_SERVERS`; Neo4j/Ollama sí traen default a `localhost` para ese caso.

## Arquitectura

Servicio REST monolítico (Spring Boot 4.1.1, Java 21) que orquesta agentes LLM. Starter `spring-boot-starter-kafka` (nuevo en Boot 4).

**Jackson 3**: el código de la app usa `tools.jackson.*` (p. ej. `JsonMapper` en `CompanyEventPublisher`), no `com.fasterxml.jackson.*`. Ojo: `app/pom.xml` todavía declara explícitamente `com.fasterxml.jackson.core:jackson-databind` y `docs/KAFKA-BUILD-FIX.md` describe el problema con la API vieja — ambos están **desactualizados** respecto al código actual; no te guíes por ellos.

### Entradas HTTP

- `CompanyController` (`/api/company`): `GET /agents` (identidad estática), `GET /agents/status` (estado real, última `AgentTask` por agente), `GET /activity` (línea de tiempo derivada de Neo4j), `POST /chat` (delega todo en `ChatIntentRouter`, ver "Command Center web" más abajo).
- `MissionController` (`/api/company/missions`): `POST` para iniciar, `GET` lista misiones recientes, `GET /{id}` estado, `GET /{id}/details` estado + tareas, `POST /{id}/decision` decisión real del inversionista humano.
- `CustomerController` (`/api/company/missions/{missionId}/...`): `POST /customers`, `POST /transactions`, `GET /net-profit` — ver "Customer Validation" más abajo.
- `LeadController` (`/api/company/leads`): `GET` lista los LEADs activos (`OpportunityMemoryService.listLeads()`), `POST /{leadId}/discard` marca uno `DESCARTADO` — ver "Flujo Opportunity → Customer candidato" más abajo.
- `SpaController`: sin API real, solo reenvía un puñado de rutas exactas de la SPA (`/`, `/chat`, `/agents`, `/missions`, `/missions/{id}`, `/activity`) a `index.html` — ver "Command Center web".

### Flujo de misión (`MissionService` → `MissionExecutor` → `AgentRuntime` → `CeoService`)

1. `MissionService.start` persiste la misión en Neo4j (`ensureMission`) y lanza `MissionExecutor.executeAsync`, devolviendo el estado inmediatamente (procesamiento en segundo plano).
2. `MissionExecutor` corre en el pool `missionOrchestratorExecutor` (2 hilos) y avanza una máquina de estados: `PLANNING → DELEGATING → WAITING_AGENT_RESULTS → EVALUATING → CONSOLIDATING → AWAITING_INVESTOR`.
3. En `DELEGATING` crea **5 tareas fijas hardcodeadas**: `sales` (MARKET_DISCOVERY), `product` (OFFER_DESIGN), `finance` (UNIT_ECONOMICS), `engineering` (DELIVERY_FEASIBILITY), `qa` (QUALITY_RISK_REVIEW — evalúa riesgos/huecos de evidencia/supuestos no verificados en la oportunidad, de forma **independiente**: corre en paralelo con las otras 4 y no tiene acceso a sus resultados, así se lo dice su propio prompt para que no alucine referencias a "lo que dijeron los demás"). Verificado en vivo: misión real con los 5 agentes completando y `qa` produciendo un `AgentResult` coherente e independiente.
4. Cada tarea se ejecuta en paralelo vía `AgentRuntime.execute` sobre el pool `agentTaskExecutor` (4–8 hilos); `AgentRuntime` construye el prompt y llama a `CeoService.executeAgentTask`.
5. Se espera a los 5 agentes (éxito o fallo, ver "Agent failure ≠ Mission failure" más abajo) y `CeoService.executeMission` consolida los resultados de los que sí completaron. La misión queda en `AWAITING_INVESTOR` — **nunca llega a `COMPLETED` automáticamente**; lo cierra el inversionista humano.

Concurrencia: **no se usa el proxy `@Async`** para la orquestación (fue un patch deliberado, ver `README.md`). Se usan executors explícitos inyectados con `@Qualifier` + `CompletableFuture.supplyAsync/runAsync`. No reintroducir `@Async` en estos caminos. `AsyncConfig` todavía lleva `@EnableAsync` y define ambos pools (`missionOrchestratorExecutor`, `agentTaskExecutor`); la anotación es inofensiva pero ningún método `@Async` la usa.

Ante cualquier excepción, `MissionExecutor.safeFail` deja la misión en `FAILED` (progreso 100). `COMPLETED` y `CANCELLED` ya tienen uso real (ver "Decisión del inversionista" más abajo) — `RESEARCHING`/`EXECUTING` del enum `MissionStatus` siguen sin ningún código que los use.

Estados de tarea (`AgentTask`, strings, no enum): `PENDING → RUNNING → COMPLETED` / `FAILED`.

Si un agente falla — tras agotar sus reintentos internos, ver "Reintento de resultados de agente" más abajo — la misión ya **no** termina automáticamente en `FAILED` por eso solo: ver "Agent failure ≠ Mission failure" más abajo. Solo si **todos** los agentes fallan no hay nada que consolidar y la misión sí falla.

### Contrato estructurado de agentes (`AgentResult`) y validación

Las tareas de agente ya no devuelven texto libre: `CeoService.executeAgentTask` le pide a Ollama structured outputs — el campo `"format"` de la llamada `AGENT_TASK` ya no es el string `"json"` (modo débil, solo garantiza JSON válido) sino el JSON Schema formal `AgentResultSchema.SCHEMA` (`agent/model/AgentResultSchema.java`), que Ollama usa para restringir la gramática de generación a la forma exacta de `AgentResult` (tipos, `enum` de `verificationStatus`/`operation`, objetos anidados `evidence`/`calculations` con `additionalProperties: false`). Verificado en vivo contra `qwen2.5-coder:7b` (Ollama 0.20.0): el modelo devuelve JSON ya conforme al schema, sin fences Markdown. `normalizeJsonResponse` se conserva como red de seguridad (limpia fences ```json ... ``` y recorta al primer `{`/último `}`) por si el modelo aún así antepone texto; si el parseo falla, lanza `IllegalStateException`.

El schema **no reemplaza** al `AgentResultValidator`: solo obliga a que la forma sea correcta, no a que el contenido sea semánticamente válido (un cálculo con aritmética incorrecta, por ejemplo, pasa el schema pero el validator lo rechaza — confirmado con una respuesta real de Ollama). Los campos de texto que el validator exige no vacíos (`agent`, `action`, `recommendation`, `Evidence.description`, `Evidence.sourceType`, `Calculation.name`) llevan `"minLength": 1` en el schema — sin eso, un agente puede devolver `recommendation: ""` (JSON válido y conforme al schema) y el validator lo rechaza igual, tumbando la tarea y, por la regla de fallo atómico, toda la misión (reproducido una vez en vivo con el agente `sales` antes de este ajuste).

**Verificado end-to-end en vivo** (`docker compose build` + `up`, misión real vía `POST /api/company/missions` contra Ollama 0.20.0 real, sin mocks): los 4 agentes (`sales`/`product`/`finance`/`engineering`) completaron con `AgentResult` válidos y la misión llegó a `AWAITING_INVESTOR` con una consolidación coherente del CEO. La consolidación en `qwen2.5-coder:14b` es la parte lenta del ciclo (~3 min en esta corrida), consistente con los benchmarks de `EMPRESA_AI_TODO.md` §5.

### Detección de contradicciones entre agentes

`ContradictionDetector` (`agent/validation/ContradictionDetector.java`) corre en `MissionExecutor`, sobre el `List<AgentResult>` completo de la misión (los 5 agentes juntos), justo antes de armar el prompt de consolidación — algo que `AgentResultValidator` no puede ver porque valida cada `AgentResult` aislado. Reglas deterministas (no otra llamada al modelo "revisándose a sí mismo"):

1. `verificationStatus=VALIDATED` con `confidence` baja (< 0.5), o `NOT_VALIDATED` con `confidence` muy alta (> 0.85).
2. El mismo nombre de `Calculation` (normalizado) reportado con resultados distintos por agentes distintos.
3. Un `Calculation.result` que supera 100x el capital semilla (`company.seed-capital-usd`) sin ninguna `Evidence.verified=true` en ese mismo `AgentResult` — el caso real documentado en `EMPRESA_AI_TODO.md` §14.2 (Costos US$52.000 / Ingresos US$600 con capital de US$50).

Si detecta algo, lo loguea (`WARN`) y lo antepone al texto que recibe `CeoService.executeMission` como bloque `CONTRADICCIONES_DETECTADAS` — no bloquea la misión ni sustituye a `AgentResultValidator`; solo obliga al CEO a verlo al consolidar. Cubierto por `ContradictionDetectorTest` (9 casos) y probado en una misión real de punta a punta (sin contradicciones esa vez, dato limpio).

Una 4ª regla, dentro de un mismo `AgentResult` (no entre agentes), ataca específicamente "no mezclar hechos con hipótesis" (`detectFactHypothesisBlending`):
1. El mismo enunciado (normalizado) no puede estar a la vez en `facts` y en `hypotheses`/`estimates`.
2. `facts` no debería contener lenguaje de cobertura típico de hipótesis/estimación (`podría`, `probablemente`, `se estima`, `aproximadamente`, `tal vez`, etc. — lista en `HEDGE_MARKERS`, en español porque el system prompt exige responder en español).

Esto es heurístico (léxico, no semántico) y puede tener falsos negativos/positivos.

**Verificado con contaminación real del modelo** (no fabricada): contra el prompt real de producción (`AgentRuntime.buildPrompt` + `AgentResultSchema`), 4 llamadas reales a `qwen2.5-coder:7b` en distintos agentes/acciones dejaron `facts` vacío o limpio — el prompt anti-alucinación actual ya es bastante disciplinado en la práctica. Para probar el detector como red de seguridad (no como re-prueba del prompt), se aisló un prompt de stress-test *sin* las reglas anti-mezcla, pidiendo explícitamente "incluye tus proyecciones como si fueran hechos confirmados": el modelo respondió con `facts: ["Capital inicial estimado: US$50.", ...]`, y `ContradictionDetector` lo atrapó correctamente por contener `'estimado'`. En ese mismo caso real, `AgentResultValidator` también lo habría rechazado (por separado) por `confidence=75` fuera de `[0,1]` — en el pipeline real, cualquiera de los dos que se ejecute primero ya tumba la tarea; son capas redundantes, no una sustituyendo a la otra.

`AgentResult` lleva `@JsonInclude(Include.NON_EMPTY)` a nivel de clase: al serializar (no al leer) omite listas vacías y strings en blanco. Esto compacta tanto el JSON que recibe el CEO en `MissionExecutor.serializeAgentResults` como lo que `AgentRuntime.toJson` persiste en Neo4j. Medido con los 4 `AgentResult` reales de una misión (`MISSION-E2E-VERIFY-2`): 2402 → 2056 caracteres (~14%). Reenviando ese mismo prompt de consolidación real contra `qwen2.5-coder:14b` (antes de este ajuste), Ollama reportó `prompt_eval_count=821` tokens — muy por debajo de los ~4075 tokens que documentaba `EMPRESA_AI_TODO.md` §12.2, porque esa cifra es de la era **previa** al contrato `AgentResult`/JSON Schema (texto narrativo libre), no comparable con el prompt estructurado actual. Con la compactación `NON_EMPTY` el ahorro adicional es modesto (~14% del payload de agentes) — la mayor parte del tamaño ya era contenido semántico real (`recommendation`, `risks`, `evidenceRequired`), no ruido de formato.

`AgentRuntime.executeInternal` pasa el `AgentResult` ya parseado por `AgentResultValidator` (una *validation gate* independiente del agente): campos obligatorios no nulos, `confidence` en `[0,1]`, cada `Calculation` recalculado (solo soporta `ADD`/`SUBTRACT`; cualquier otra operación es un error), cada `Evidence` con `description`/`sourceType` y `source` si `verified=true`, y `verificationStatus` restringido a `NOT_VALIDATED|PARTIALLY_VALIDATED|VALIDATED` — `VALIDATED` exige al menos una evidencia `verified=true` con `source`. Un resultado inválido (o un fallo de parseo) ya no tumba la tarea al primer intento — ver el punto siguiente.

### Reintento de resultados de agente

`AgentRuntime.executeInternal` reintenta hasta `MAX_RESULT_RETRIES + 1` veces (hoy: 3 intentos) tanto si `CeoService.executeAgentTask` lanza excepción (Ollama no devolvió JSON parseable) como si `AgentResultValidator` rechaza el resultado ya parseado. En cada reintento, el motivo exacto del rechazo (mensaje de la excepción o `validation.errors()`) se antepone al prompt del siguiente intento como bloque `CORRECCIÓN DEL INTENTO ANTERIOR`, pidiéndole al agente corregir solo eso — no es "el modelo revisándose a sí mismo" (evitado deliberadamente en otras partes del código, ver `ContradictionDetector`/`EvidenceValidationGate`): el feedback viene siempre de una fuente determinista (la excepción de parseo, o los errores de `AgentResultValidator`), nunca de que el propio modelo se autoevalúe. Solo tras agotar todos los intentos se lanza la `IllegalStateException` que tumba la tarea (y, por la regla de fallo atómico, la misión). A partir del intento 2 se publica `EMPRESA_TASK_RETRY` a Kafka (`data.status=RETRYING`); el intento 1 no genera este evento. `EvidenceValidationGate` queda **fuera** de este bucle — sigue fallando la tarea de inmediato sin reintento (asimetría deliberada, no tocada en este cambio). Cubierto por `AgentRuntimeTest` (5 casos: éxito directo, reintento por rechazo del validator, reintento por fallo de parseo, y agotamiento de reintentos en ambos casos) y verificado en vivo con una misión real (sin necesidad de reintento esa vez — dato limpio; la instrumentación `inference attempt=N` confirma que el código está activo).

`CeoService.executeAgentTask` todavía conserva un bloque grande comentado (una versión anterior del mismo parseo) — es código muerto, no una ruta alternativa activa; no dupliques lógica a partir de él.

### Agent failure ≠ Mission failure

Antes, `MissionExecutor` esperaba a los 5 agentes con `CompletableFuture.allOf(futures).join()`: si **cualquiera** agotaba sus reintentos, `.join()` propagaba esa excepción, el `catch` externo mandaba la misión entera a `FAILED`, y se descartaban los resultados de los agentes que sí habían completado — un solo agente no recuperable tumbaba todo el trabajo real de los demás.

Ahora `MissionExecutor.executeInternal` espera cada future por separado (`futuresByAgent`, un `LinkedHashMap<agentId, CompletableFuture<AgentResult>>`) y captura éxito/fallo en un `AgentExecutionOutcome` (`model/AgentExecutionOutcome.java` — deliberadamente sin `recoverable`/`attempts` como sugiere `EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §21: esos campos no tienen una fuente real en el código hoy, y el detalle de reintentos ya es público vía `EMPRESA_TASK_RETRY`):

- Si **todos** los agentes fallan, no hay nada que consolidar — la misión sí termina en `FAILED` (mismo camino que antes).
- Si **al menos uno** completó, la misión sigue: `serializeAgentResults`/`ContradictionDetector` operan solo sobre los que completaron, y el texto que recibe `CeoService.executeMission` incluye un bloque nuevo `AGENTES_FALLIDOS` (mismo patrón que `CONTRADICCIONES_DETECTADAS`) listando qué agente falló y por qué — para que sea la consolidación del CEO, no un `catch` genérico, la que decida cómo tratar el hueco.

Cubierto por `MissionExecutorTest` (5 casos: todos completan, uno falla y la misión sigue, todos fallan y la misión sí falla, y los 2 de replanificación de abajo). **Disparado de verdad en producción** (no solo en el test): en una misión real, `sales` agotó sus 3 intentos por un cálculo que oscilaba sin converger (`Cálculo inconsistente: ... expected=102.93 actual=-101.93`, luego `expected=202.93` en el intento 3 — el modelo nunca corrigió el signo) y su tarea quedó `FAILED` en Neo4j; los otros 4 agentes completaron y la misión llegó a `AWAITING_INVESTOR` con la consolidación del CEO incluyendo una sección explícita **"5. Agentes Fallidos"**: *"El agente de ventas presentó problemas técnicos que impedieron completar su tarea, por lo que los resultados relevantes son parciales..."* — exactamente el comportamiento diseñado, no una simulación.

### Replanificación automática

`EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §32 deja esto dentro de "Autonomía avanzada" sin diseño concreto (a diferencia de Evidence Acquisition, que sí traía pseudocódigo) — el alcance real se acordó con el usuario antes de escribir código: reintentar automáticamente **solo** los agentes que fallaron (no la misión completa), con un límite de reintentos a nivel de misión distinto del interno de `AgentRuntime`.

Un agente que agota sus 3 intentos internos (`AgentRuntime.MAX_RESULT_RETRIES`) todavía no se acepta como definitivamente fallido: `MissionExecutor.replanFailedAgents` le da hasta `MAX_AGENT_REPLANS` (hoy: 1) oportunidades más de correr su tarea **desde cero** (turno de decisión + turno final nuevos vía `runtime.execute`, no una continuación del intento fallido) antes de incluirlo en `AGENTES_FALLIDOS`. Cada intento de replan publica `EMPRESA_MISSION_REPLANNED` (`missionId`/`taskId`/`agentId`, `data.replanAttempt`/`data.previousError`) — sugerido en `EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §22, ahora con una funcionalidad real detrás, no solo el nombre del evento. `MAX_AGENT_REPLANS=1` deliberadamente bajo: es una segunda oportunidad completa, no una corrección incremental — si tampoco funciona a la segunda, insistir más solo alarga la misión sin cambiar el resultado.

`definitions` (los 5 agentes fijos de `DELEGATING`) pasó de `List<String[]>` a un record local `AgentDefinition(agentId, action, objective)` — necesario para poder volver a mirar la acción/objetivo de un agente por su id durante el replan, no solo recorrerlos linealmente una vez.

Cubierto por `MissionExecutorTest` (2 casos nuevos: el agente se recupera en el replan y la misión llega a `AWAITING_INVESTOR` sin `AGENTES_FALLIDOS`; el replan también falla y se agota en `MAX_AGENT_REPLANS`, cayendo en el mismo camino de resultado parcial de arriba). Verificado en vivo con una misión real completa tras el cambio: los 5 agentes completaron en el intento 1 (sin necesitar replan), confirmando que el cambio no rompió el camino normal — el camino de recuperación en sí está probado con los mocks de `MissionExecutorTest` porque forzar una falla real y determinista de un solo agente en producción (sin afectar a los demás) requeriría sabotear Ollama selectivamente, algo que no hay una forma limpia de hacer.

### Evidence Binding: "buscó pero no citó"

Tercer gate dentro del **mismo** bucle de reintento que `AgentResultValidator` (a diferencia de `EvidenceValidationGate`, que sigue fallando la tarea de inmediato sin reintento): `EvidenceBindingGate` (`agent/validation/EvidenceBindingGate.java`) detecta el caso en que un agente pidió `search_web_evidence`, recibió URLs reales y confirmadas (`ClaimRelevanceChecker` + `confirmReachable`), y aun así su `AgentResult` final no cita ninguna en `evidence[]` — antes de este gate nada impedía que eso pasara silenciosamente; ni `AgentResultValidator` ni `EvidenceValidationGate` comparan el resultado contra lo que realmente se le entregó al modelo en el turno de herramienta, solo miran el `AgentResult` en aislamiento.

Para que `AgentRuntime` pueda hacer esa comparación, `CeoService.executeAgentTask` ya no devuelve un `AgentResult` suelto sino `AgentTaskOutcome(result, confirmedEvidenceUrls)` (`agent/model/AgentTaskOutcome.java`) — `confirmedEvidenceUrls` son las URLs que de verdad sobrevivieron `confirmReachable` en el turno de herramienta de esa llamada (vacío si no hubo tool call, o si ninguna sobrevivió). `EvidenceBindingGate.check(confirmedEvidenceUrls, result)` compara esas URLs (normalizadas: minúsculas, sin `/` final) contra los `source` de `result.evidence()`; si `confirmedEvidenceUrls` está vacío, no hay nada que exigir (pasa trivialmente). Si hay URLs confirmadas y ninguna aparece citada, rechaza con el mismo mecanismo de `AgentResultValidator`: el motivo entra al bloque `CORRECCIÓN DEL INTENTO ANTERIOR` del siguiente intento, y solo tras agotar los reintentos se lanza `IllegalStateException` (tarea `FAILED` → misión `FAILED`, misma regla de fallo atómico).

**`confirmedEvidenceUrls` se acumula entre intentos, no se sobrescribe**: el turno de decisión de herramienta de `CeoService` es independiente en cada intento (no ve el feedback de corrección), así que un reintento puede perfectamente no volver a pedir la herramienta. `AgentRuntime.executeInternal` guarda las URLs confirmadas en un `LinkedHashSet` que se va uniendo (`addAll`) en cada intento, nunca reasignando — si se sobrescribiera, una URL real confirmada en el intento 1 se "olvidaría" en el intento 2 y el gate aprobaría trivialmente un resultado que sigue sin citar nada real. Bug encontrado y corregido en revisión propia antes de que causara un falso negativo en producción (no fue reportado por el usuario ni observado fallando).

Cubierto por `EvidenceBindingGateTest` (8 casos aislados, sin Neo4j/Ollama) y por 3 casos en `AgentRuntimeTest` (reintento cuando no cita, agotamiento cuando nunca cita, y el caso específico de acumulación: intento 1 busca y no cita, intento 2 no vuelve a buscar y tampoco cita — debe seguir rechazado — intento 3 cita y pasa).

### Evidence Engine y Validation Gate semántica

Separado deliberadamente de `AgentResultValidator` (sintáctico) y de `ContradictionDetector` (cruza agentes/campos): `EvidenceValidationGate` (`agent/validation/EvidenceValidationGate.java`) valida que lo que un agente marca como `verified=true` sea, al menos superficialmente, creíble — "el agente afirma X" ≠ "la empresa puede demostrar X" (`EMPRESA_AI_TODO.md` §17):

1. `sourceType` debe ser uno de `WEB|CUSTOMER|TRANSACTION|INTERNAL|NONE` (las mismas categorías que ya pide `AgentRuntime.buildPrompt`; antes nada validaba que el modelo respetara esa lista).
2. `verified=true` con `sourceType=NONE` es una contradicción directa (verificado sin ninguna fuente real) — rechazado.
3. `verified=true` con `sourceType=WEB` exige que `source` empiece con `http://`/`https://` — una evidencia WEB "verificada" sin nada parecido a una URL es sospechosa.

Corre en `AgentRuntime.executeInternal` justo después de `AgentResultValidator`, como un segundo gate duro: si falla, lanza `IllegalStateException` igual que el validator sintáctico (misma consecuencia: tarea `FAILED` → misión `FAILED`). Cubierto por `EvidenceValidationGateTest` (7 casos).

La parte de **persistencia** del Evidence Engine: `MissionMemoryService.recordEvidence` escribe cada `AgentResult.Evidence` como un nodo `Evidence` de primera clase en Neo4j (constraint de unicidad `evidence_id` en `CompanyMemoryService.initializeSchema`), enlazado `(:AgentTask)-[:HAS_EVIDENCE]->(:Evidence)` — ya no vive solo como texto dentro del blob JSON de `AgentTask.result`. Se llama desde `AgentRuntime` una vez que ambos gates (sintáctico + semántico) pasan. Verificado en vivo: misión real completa, `MATCH (t:AgentTask)-[:HAS_EVIDENCE]->(e:Evidence)` devolvió el nodo esperado con los campos correctos.

**Deduplicación de evidencia** (`EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §17): el id del nodo ya **no** es `"{taskId}-EVIDENCE-{índice}"` (garantizaba un nodo nuevo por tarea, aunque dos agentes citaran exactamente la misma fuente) sino `EvidenceDedupKey.stableId(source, description)` (`evidence/EvidenceDedupKey.java`) — `SHA-256` de `source`+`description` normalizados (minúsculas, sin espacios de más, sin `/` finales). Si dos tareas citan la misma evidencia (misma fuente, misma descripción), el `MERGE` de Cypher apunta al mismo nodo: cada tarea igual gana su propia relación `HAS_EVIDENCE` hacia él (se puede consultar cuántos agentes corroboraron el mismo dato con `MATCH (e:Evidence)<-[:HAS_EVIDENCE]-(t) RETURN count(t)`), pero el contenido del nodo solo se fija en la primera escritura (`ON CREATE SET`) — las citas siguientes solo refrescan `updatedAt` (`ON MATCH SET`), no pisan `agentId`/`missionId` del primer agente que la encontró. Deliberadamente **no** se restringe por misión: la misma fuente+descripción encontrada en misiones distintas también deduplica — es la misma evidencia real sin importar quién ni cuándo la vio. Cubierto por `EvidenceDedupKeyTest` (7 casos, la función de hashing es pura y se testea sin Neo4j, igual que `ClaimRelevanceChecker`) y verificado en vivo reproduciendo a mano la consulta Cypher real de `recordEvidence` dos veces con la misma fuente+descripción desde dos `AgentTask` distintos: un solo nodo `Evidence`, `agentId` del primer escritor intacto, 2 relaciones `HAS_EVIDENCE` (una por tarea).

`neo4j/init.cypher` (la referencia manual) **no** incluye ningún `CREATE CONSTRAINT` — ya estaba desincronizado de `CompanyMemoryService.initializeSchema()` antes de este cambio (solo tiene el seed de `Company`/`Agent`); no te guíes por él para el esquema de constraints, solo para el seed.

### Customer Validation (`CustomerController` → `CustomerService` → `CustomerMemoryService`)

Registrar un cliente o una venta **real** es un flujo separado del de misiones — no pasa por un `AgentResult` ni por un LLM. Hoy es un canal de entrada de datos (pensado para el fundador humano; no hay ningún flujo que permita a un agente llamarlo autónomamente):

- `POST /api/company/missions/{missionId}/customers` (`CustomerCommand`): registra un `Customer`, exige una `Evidence` (misma forma que la de `AgentResult`: `description`/`source`/`sourceType`/`verified`) que pasa por el **mismo** `EvidenceValidationGate` que usan los agentes (`evidenceGate.validate(List<Evidence>)`, sobrecarga nueva que no depende de `AgentResult`) — un `verified=true` con `sourceType=NONE`, por ejemplo, se rechaza igual que si lo hubiera declarado un agente. 404 si la misión no existe (`IllegalArgumentException`, sin handler global → 500; no hay manejo de errores HTTP más fino en ningún controller de este proyecto, se mantiene esa convención).
- `POST /api/company/missions/{missionId}/transactions` (`TransactionCommand`): registra una venta ligada a un `customerId` ya existente (404 si no existe — `Optional` vacío desde `CustomerMemoryService`, mismo patrón que `MissionController`), calcula `netProfitUsd = revenueUsd - costUsd`, y exige su propia evidencia (recibo, comprobante, contrato).
- `GET /api/company/missions/{missionId}/net-profit`: suma todas las `Transaction` de la misión y devuelve `netProfitUsd`, `successCriterionMet` (`> company.seed-capital-usd`) y `successLevel` (`NINGUNO|BUENO|MUY_BUENO|EXCELENTE|EXTRAORDINARIO`, umbrales fijos de `EMPRESA_AI_TODO.md` §2.4: >US$50, >US$100, ≥US$1.000, ≥US$5.000 — no escalan con el capital semilla configurado, son los niveles de éxito documentados).

Grafo: `(:Mission)-[:HAS_CUSTOMER]->(:Customer)-[:HAS_EVIDENCE]->(:Evidence)`, `(:Mission)-[:HAS_TRANSACTION]->(:Transaction)-[:FOR_CUSTOMER]->(:Customer)`, `(:Transaction)-[:HAS_EVIDENCE]->(:Evidence)` (un solo nodo `Evidence` por registro, id `"{customerId|transactionId}-EVIDENCE"`; a diferencia de `MissionMemoryService.recordEvidence`, aquí el `agentId` guardado es el literal `"human"`).

Verificado en vivo de punta a punta (misión creada directamente en Neo4j para no esperar una orquestación completa, ya verificada por separado): evidencia inválida → rechazada; cliente válido → creado; venta a cliente inexistente → 404; venta válida → `netProfitUsd` correcto; `GET /net-profit` agregando bien sobre múltiples transacciones; estructura del grafo confirmada con Cypher. 7 tests en `CustomerServiceTest`.

### Flujo Opportunity → Customer candidato (`OpportunityMemoryService`) — automático, 100% nivel 🟢

Alcance acordado con el usuario antes de escribir código, porque el flujo completo que describe `EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §19 (`Opportunity → Customer candidate → contact → interés real → offer → transaction`) incluye pasos ("contact", cerrar una venta) que caen en el nivel 🔴 de `empresa.md` §5 ("vender o transferir activos", "acciones irreversibles") — requieren aprobación humana, no automatización. Lo que sí es 100% nivel 🟢 (`"analizar mercados"`, `"buscar nuevas oportunidades"`) y se automatizó:

- **`Opportunity`**: antes existía solo como constraint de Neo4j (`opportunity_id`), nunca se creaba ningún nodo. Ahora `MissionExecutor` llama a `OpportunityMemoryService.recordOpportunity(missionId, instruction)` siempre que la misión produce al menos un resultado (mismo punto que ya calcula `agentResults`) — un nodo `Opportunity {status:'IDENTIFIED'}` por misión, `(:Mission)-[:HAS_OPPORTUNITY]->(:Opportunity)`. `status` nunca pasa de `IDENTIFIED` automáticamente: decidir si una oportunidad está validada es del inversionista humano, no de este servicio.
- **Customer candidato (LEAD)**: `AgentResult` gana un campo opcional `customerCandidates: List<CustomerCandidate>` (`name`/`description`/`source`/`sourceType`/`confidence`, sin `verified` — un candidato de agente nunca es una relación real confirmada). Constructor de compatibilidad de 12 args conservado (delega con `List.of()`) para no tocar los `new AgentResult(...)` ya existentes en los tests. `AgentResultSchema` lo agrega como campo `required` (mismo patrón que el resto: el modelo siempre lo emite, vacío por defecto — verificado en vivo, sin errores de parseo). El prompt (`AgentRuntime.buildPrompt`) instruye explícitamente no inventar candidatos genéricos. `OpportunityMemoryService.recordCandidate` persiste cada uno como `Customer {status:'LEAD'}` (`(:Opportunity)-[:HAS_CANDIDATE]->(:Customer)`, evidencia con `verified=false` siempre) — **deliberadamente una relación distinta** de `(:Mission)-[:HAS_CUSTOMER]->(:Customer)` que usa el flujo humano de `CustomerMemoryService`, para no tocar ese código ya probado. Ambos pueden compartir el label `Customer` (son la misma idea en distintas etapas — LEAD/PROSPECT/CUSTOMER/PAYING_CUSTOMER) pero llegan por caminos separados; las relaciones (`HAS_CANDIDATE` vs `HAS_CUSTOMER`) siguen siendo deliberadamente distintas.

**Puente LEAD → cliente real**: `CustomerCommand` gana un campo opcional `leadId`. Si viene no vacío, `CustomerService.registerCustomer` valida la evidencia primero (ver orden abajo) y solo después llama a `OpportunityMemoryService.markConverted(leadId)` (compara-y-actualiza `status='LEAD'` → `'CONVERTIDO'` en una sola sentencia Cypher; `false`/vacío si el lead no existe o ya cambió de estado → `IllegalStateException`) y rechaza con `IllegalArgumentException` si `customerId` es igual al `leadId` (evitaría que el `MERGE` del cliente real aterrice sobre el propio nodo LEAD). `CustomerMemoryService.registerCustomer` enlaza el `Customer` real nuevo al LEAD del que salió vía `(:Customer)-[:CONVERTED_FROM]->(:Customer {status:'CONVERTIDO'})`. **Orden importante**: la evidencia se valida *antes* de tocar el lead — si fuera al revés, evidencia inválida dejaría el lead `CONVERTIDO` sin ningún cliente creado (`CONVERTIDO`/`DESCARTADO` son terminales, sin endpoint de revertir). **Límite conocido, no resuelto** (mismo criterio que el DNS rebinding de `WebPageFetcher`): `markConverted` y `registerCustomer` escriben en dos transacciones Neo4j separadas, no atómicas entre sí — si la segunda falla después de que la primera ya tuvo éxito, el lead queda `CONVERTIDO` sin cliente creado (recuperable solo a mano por Cypher).

Cubierto por 11 casos en `CustomerServiceTest`, 3 en `LeadControllerTest` y el intent `LEADS` en `ChatIntentRouterTest`. **Verificado en vivo de punta a punta** contra el stack real (Docker: `company-core` reconstruido desde esta rama + Neo4j + Kafka + Ollama), sembrando 3 LEADs directamente en Neo4j sobre una misión de `TEST` (mismo patrón que la verificación de `CustomerServiceTest`, sin esperar una orquestación completa): `GET /leads` los listó junto a los LEADs reales ya existentes de misiones anteriores; `POST /{leadId}/discard` lo pasó a `DESCARTADO` y la respuesta reflejó `discardReason`/`discardedAt` reales; un intento de conversión con evidencia semánticamente inválida (`verified=true`, `sourceType=NONE`) falló con 500 y el LEAD **permaneció en `LEAD`** (confirma en vivo el fix del orden crítico: antes de este fix, este mismo caso lo dejaba `CONVERTIDO` huérfano — reproducido y corregido en la revisión final de esta rama, no solo en el test unitario); un intento con `customerId` igual al `leadId` fue rechazado con `IllegalArgumentException` sin tocar el LEAD; una conversión válida creó el `Customer` real (`status` ausente, no `NULL` literal — cuenta como cliente real) enlazado por `CONVERTED_FROM` al LEAD, que pasó a `CONVERTIDO`; el conteo agregado (`customers=1, prospects=21, convertidos=1, descartados=1`) confirmó que no hay doble conteo; y el chat (`POST /chat`, `"qué leads tengo para contactar"`) devolvió la lista real y determinística sin pasar por Ollama, excluyendo correctamente el LEAD convertido y el descartado.

Cubierto por `MissionExecutorTest` (2 casos nuevos: se registra la Opportunity siempre, se registran candidatos cuando un agente los reporta). Verificado en vivo con una misión real: 4 de 5 agentes (`sales`, `product`, `finance`, `engineering`) reportaron candidatos reales (10 en total, con URLs reales como fuente), todos persistidos como `Customer {status:'LEAD'}` correctamente enlazados a la `Opportunity` de la misión.

Los campos `List<String>` de `AgentResult` (`facts`, `hypotheses`, `estimates`, `evidenceRequired`, `risks`) usan `@JsonDeserialize(contentUsing = LenientStringDeserializer.class)` (`agent/model/LenientStringDeserializer.java`): si el modelo devuelve un objeto en vez de un string para alguno de esos elementos (bug real observado con Ollama, p. ej. `evidenceRequired: [{"description": "..."}]`), el deserializador rescata `description`/`text`/`value`/`content`/`name`/`detail`/`summary` si existe, o cae al JSON crudo como string — nunca lanza excepción de parseo por esto.

Compila igual porque Maven no exige esa correspondencia, pero al buscarlo por ruta de paquete no está donde se esperaría.

### Memoria: Neo4j

### Relaciones funcionales (auditoría contra el modelo objetivo §23)

`EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §23 muestra el grafo objetivo como `(:Company)+--(:Mission)+--(:Agent)+--(:Evidence)` y `(:Mission)+--(:Opportunity)+--(:Customer)+--(:Transaction)+--(:Evidence)` — auditar contra esto (alcance acordado con el usuario: solo entidades que ya existen, no los 21 labels especulativos de "autonomía avanzada" como `Role`/`Prediction`/`CapitalAllocation`, que siguen sin ningún código que los escriba o los lea) encontró dos huecos reales, ambos cerrados:

1. **Mission no tenía relación directa con sus agentes delegados** (solo con el CEO vía `LED_BY`) — la única conexión era indirecta, vía `AgentTask`. `MissionMemoryService.createTask` ahora también hace `MERGE (m)-[:INVOLVES_AGENT]->(a)`, así que cada uno de los 5 agentes de una misión queda directamente enlazado a ella, sin tener que atravesar `AgentTask`.
2. **Los clientes reales (humanos, vía `CustomerController`) colgaban solo de Mission, nunca de Opportunity** — a diferencia de los candidatos LEAD de agentes (que sí cuelgan de Opportunity vía `HAS_CANDIDATE`), rompiendo la cadena `Mission→Opportunity→Customer` del modelo objetivo para el caso real. `CustomerMemoryService.registerCustomer` ahora también intenta `MATCH (o:Opportunity {id:...}), (c:Customer {id:...}) MERGE (o)-[:HAS_CUSTOMER]->(c)` — deliberadamente un `MATCH` normal, no `MERGE` de la Opportunity: si la misión aún no llegó a consolidación (la Opportunity todavía no existe), el `MATCH` simplemente no encuentra nada y no pasa nada — nunca crea una Opportunity vacía como efecto secundario de registrar un cliente. El cliente sigue quedando enlazado directo a Mission igual que antes (no se rompió nada del flujo existente).

Verificado en vivo: (a) una misión real nueva mostró los 5 agentes conectados vía `INVOLVES_AGENT` apenas se crean las tareas; (b) registrar un cliente real contra una misión que ya tenía Opportunity dejó el cliente enlazado por **ambos** caminos (`Mission→Customer` y `Opportunity→Customer`); (c) registrar un cliente real contra una misión sin Opportunity confirmó 0 nodos `Opportunity` creados como efecto secundario, y el cliente igual quedó creado por el camino directo de siempre.

### Decisión del inversionista humano (`MissionController.decide` → `MissionService.recordDecision`)

Primera entidad real del grupo "Company Memory" que antes era solo un constraint de Neo4j sin ningún nodo (`Decision`, ver más abajo). Alcance acordado con el usuario antes de escribir código: de los 5 tipos que agrupaba esta fila del roadmap (`Decision`/`Lesson`/`Strategy`/`Prediction`/`CapitalAllocation`), **solo `Decision` tiene hoy un disparador real y no fabricado** — los otros 4 exigirían inventar juicios de negocio (aprender de ventas que todavía no existen, repartir un capital que hoy no se reparte en portafolio) y quedan pendientes hasta que haya datos reales de negocio de los que partir.

`POST /api/company/missions/{missionId}/decision` (`DecisionCommand{decision: APPROVE|REJECT|REQUEST_MORE_EVIDENCE, reasoning}`): es exactamente el punto de `empresa.md` §5 nivel 🔴 ("decisiones estratégicas importantes") donde antes la misión se quedaba parada para siempre en `AWAITING_INVESTOR` sin ningún lugar donde el fundador humano registrara su decisión real. Solo se acepta sobre una misión en `AWAITING_INVESTOR` o `FAILED` (`IllegalStateException` si no, mismo patrón sin manejo fino de errores HTTP del resto del proyecto → 500); 404 si la misión no existe.

- `APPROVE` → `MissionStatus.COMPLETED` (primer uso real de este valor del enum, antes definido pero sin código que lo asignara).
- `REJECT` → `MissionStatus.CANCELLED` (ídem, primer uso real).
- `REQUEST_MORE_EVIDENCE` → no cambia el estado de la misión, solo registra la decisión — no hay todavía un mecanismo de re-ejecución automática para este caso, el fundador decide manualmente qué hacer después.

Una misma misión puede acumular varias decisiones (p. ej. un `REQUEST_MORE_EVIDENCE` seguido de un `APPROVE` final) — `decisionId` incluye un timestamp a propósito, no es idempotente sobre el mismo id como sí lo son los registros de evidencia. `MissionMemoryService.recordDecision` persiste `(:Mission)-[:HAS_DECISION]->(:Decision {decision, reasoning, decidedAt})`. Publica `EMPRESA_MISSION_DECISION_RECORDED` (`agentId="human"`, `data.decision`/`data.reasoning`) siempre, más el `EMPRESA_MISSION_UPDATED` normal cuando sí cambia el estado (`APPROVE`/`REJECT`).

Cubierto por 6 casos en `MissionServiceTest`. Verificado en vivo de punta a punta: `REQUEST_MORE_EVIDENCE` sobre una misión real no cambió su estado; `APPROVE` la dejó en `COMPLETED`; sobre otra misión, `REJECT` la dejó en `CANCELLED`; un intento de decidir de nuevo sobre la misión ya `COMPLETED` fue rechazado (500); los 3 eventos `EMPRESA_MISSION_DECISION_RECORDED` reales aparecieron en `EMPRESA_EVENTS`; y Cypher confirmó las 2 decisiones de la primera misión persistidas en orden con su `reasoning` real.

**Groundwork de memoria ampliada** (`CompanyMemoryService.initializeSchema`, sección separada con comentario): constraints de unicidad `id` para 20 labels más del roadmap de `EMPRESA_AI_TODO.md` §21 / `status.md` §17 — `Role`, `RoleVersion`, `AgentVersion`, `Prediction`, `PredictionOutcome`, `CredibilityScore`, `CapitalAllocation`, `Investment`, `Portfolio`, `GovernanceRule`, `GovernanceAmendment`, `Model`, `ModelAssignment`, `Tool`, `ToolVersion`, `PublicDecision`, `Customer`, `Transaction`, `Lesson`, `Strategy` (`Decision` ya salió de esta lista — ver arriba). **Deliberadamente solo el constraint de identidad** — sin propiedades ni relaciones definidas, porque ningún flujo del código las escribe o las lee todavía (son para features que no existen aún: organización autoevolutiva, mercado de predicción, cartera de capital, gobernanza, gabinete multi-modelo, auto-mejora de herramientas, transparencia pública). Cuando se implemente cada funcionalidad, ahí se definen las propiedades y relaciones reales según lo que esa funcionalidad concreta necesite — no hay un diseño de grafo ya decidido más allá del label y el `id`. Verificado en vivo con `SHOW CONSTRAINTS` contra el Neo4j real tras `docker compose up`.

Deliberadamente no se implementó `EMPRESA_EVIDENCE_CANDIDATE_CREATED` (lo sugiere `EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §22): sería redundante con `candidatesFound` de `SEARCH_COMPLETED` y multiplicaría el volumen de eventos sin aportar información nueva. Verificado en vivo consumiendo `EMPRESA_EVENTS` de punta a punta para una misión real de 5 agentes: 5 `SEARCH_STARTED`, 5 `SEARCH_COMPLETED`, 12 `VERIFIED`, 33 `REJECTED` — incluyendo un rechazo real por el límite de tamaño de `WebPageFetcher` (2 MB), no solo por relevancia o error de red.

**Métricas de Evidence Acquisition** (`/actuator/metrics`, `management.endpoints.web.exposure.include` ahora incluye `metrics`): distintas de los eventos Kafka de arriba — esos son un registro de ocurrencias discretas (para auditar/reproducir una tarea puntual), esto son series numéricas agregables (para dashboards/alertas: tasas, percentiles de latencia). `CeoService.executeTool` usa `MeterRegistry` (Micrometer, ya en el classpath vía `spring-boot-starter-actuator`, sin dependencia nueva) para: `evidence.search.requests` (contador, tag `agent`), `evidence.search.duration` (timer de la llamada real a `searchEvidence`, tag `agent`), `evidence.candidate.verified` (contador, tag `agent`), `evidence.candidate.rejected` (contador, tags `agent`+`reason` = nombre simple de la excepción — no el mensaje completo, para no explotar cardinalidad) y `evidence.candidate.duration` (timer de `confirmReachable` por candidato, tags `agent`+`outcome=verified|rejected`). No se agregó `micrometer-registry-prometheus`: sin un exportador registrado, Spring Boot igual autoconfigura un `SimpleMeterRegistry` en memoria, suficiente para consultar via `/actuator/metrics/{nombre}` — si más adelante se conecta Prometheus/Grafana (como ya tienen otros proyectos de esta máquina), alcanza con agregar esa dependencia, el código de instrumentación no cambia. Verificado en vivo contra una misión real: `evidence.search.requests` count=6 (desglosable por agente: qa/product/engineering/sales/finance), `evidence.search.duration` count=6 con `MAX`=4.36s, `evidence.candidate.verified` count=19, `evidence.candidate.rejected` count=32 (`reason=IllegalStateException` en esa corrida), `evidence.candidate.duration` count=51 (=19+32) con tags `agent`/`outcome` — los 5 endpoints respondieron con datos reales, no vacíos.

### LLM: Ollama

`CeoService` es el **único** cliente de Ollama: `RestClient` POST a `/api/chat`, no streaming. Usa dos modelos distintos según el rol: CEO en `qwen2.5-coder:14b` para razonamiento/consolidación (notablemente más lento, ver `EMPRESA_AI_TODO.md` §5), agentes en `qwen3:8b` para ejecución paralela — cambiado desde `qwen2.5-coder:7b` tras comparar ambos en vivo (ver "Modelo de agente" más abajo). Las tareas de agente (`executeAgentTask`) hacen hasta dos llamadas por intento (`AGENT_TOOL_CALL` con `tools`, luego `AGENT_TASK` con `format: AgentResultSchema.SCHEMA` — nunca ambos a la vez, ver "Evidence Acquisition" más abajo); el chat del CEO y la consolidación de misión son una sola llamada sin `format` ni `tools`. Todos los system/user prompts están en español y son fuertemente anti-alucinación: los agentes no deben inventar clientes, ventas, ingresos, búsquedas web ni evidencia, y deben separar hecho / hipótesis / estimación / resultado verificado.

### Evidence Acquisition (`com.aicompany.core.evidence.*`) — módulo standalone, **no conectado todavía** al flujo de misiones

Primera pieza de `EMPRESA_AI_NUEVO_TODO_EVIDENCE.md`. Búsqueda web + recuperación de páginas, con dos capas deliberadamente separadas (§12 del doc):

- `EvidenceCandidate` (`claim`/`url`/`title`/`snippet`/`sourceType`): un resultado de búsqueda, **sin** `verified` — a propósito distinto de `AgentResult.Evidence`, porque encontrar una URL no es evidencia.
- `WebSearchPort` (interfaz) + `SerperSearchAdapter` (única implementación hoy): la búsqueda queda desacoplada del proveedor a propósito — agregar otro proveedor más adelante no debería tocar `EvidenceAcquisitionService`. Historial de por qué se llegó a Serper (los tres proveedores anteriores se descartaron con evidencia real, no por suposición):
  1. **DuckDuckGo HTML/Lite** (scraping directo, sin key): bloqueó con un challenge anti-bot (CAPTCHA) ya en la segunda petición, probado en vivo. Ni siquiera un "navegador" propio (curl/lynx/headless) lo evita — el bloqueo es detección del lado del servidor por comportamiento/IP, no por el cliente HTTP usado; y el CAPTCHA es un puzzle de imágenes que ningún automatismo resuelve sin un servicio externo de resolución.
  2. **Brave Search API**: se creyó que tenía tier gratuito sin tarjeta — **incorrecto**, lo eliminó en febrero de 2026; hoy exige tarjeta de crédito registrada (con $5/mes de crédito gratis). Verificado con búsqueda web antes de implementar nada, tras la corrección del usuario.
  3. **Serper** (`google.serper.dev`): 2.500 consultas gratis, **sin tarjeta**, verificado en su documentación oficial — proxy de resultados reales de Google, acceso autorizado (no scraping no autorizado de la página de resultados de un buscador, con el riesgo legal/ToS que eso implica).
  
  `SerperSearchAdapter` usa `POST /search` (no GET con query params como Brave), header `X-API-KEY`, body `{q, gl, hl, num}`, respuesta con array top-level `organic[]` (`title`/`link`/`snippet` — no `url`/`description` como Brave). Llama a `evidence.web-search.base-url` (`EVIDENCE_WEB_SEARCH_BASE_URL`, default `https://google.serper.dev`) / `EVIDENCE_WEB_SEARCH_API_KEY` (vacío por default). `parseResults(String)` es package-private a propósito para poder testear el parseo sin red ni API key.
- `WebPageFetcher`: recupera una URL real, con protección SSRF real (no un stub) — bloquea `localhost`, loopback, rangos privados (`10.x`, `172.16.x`, `192.168.x`), link-local (incluye el endpoint de metadata de nube `169.254.169.254`), exige `http`/`https`, no sigue redirects (para que una validación no se burle vía redirect), timeout de conexión/lectura, y límite de tamaño de respuesta (2 MB) con lectura acotada por stream (no lee todo a memoria antes de medir). Limitación conocida y **no resuelta**: no protege contra DNS rebinding (la IP se resuelve una vez, antes de conectar; no hay pinning de conexión a esa IP resuelta).
- `EvidenceAcquisitionService.searchEvidence(query)` → `List<EvidenceCandidate>` (usa `evidence.web-search.country`/`.language` como default por si el llamador no los especifica). `confirmReachable(candidate)` → `AgentResult.Evidence` con **`verified=false` siempre** — confirma que la URL respondió con contenido *y* que ese contenido está relacionado con el `claim` (ver `ClaimRelevanceChecker` justo abajo), no que el dato concreto esté verificado. Esto es una desviación deliberada del código de referencia del doc (que en su §11 marcaba `verified=true` solo por un fetch exitoso); hacerlo así habría contradicho todo lo que `AgentResultValidator`/`EvidenceValidationGate`/`ContradictionDetector` ya hacen en este proyecto para que un `verified=true` signifique algo real.
- **Verificación semántica (`ClaimRelevanceChecker`, `evidence/ClaimRelevanceChecker.java`)**: heurística léxica determinista (sin modelo — no es "el modelo revisándose a sí mismo"), no NLP real. Normaliza claim y contenido (minúsculas, sin tildes), extrae los términos significativos del claim (≥3 letras, fuera de una lista de stopwords en español) y calcula qué fracción aparece literalmente en el contenido; `supported()` exige ≥30% de coincidencia. `confirmReachable` la llama después del fetch: si no se supera el umbral, lanza `IllegalStateException` con el ratio exacto (`"(m/n términos coincidieron)"`) y la fuente **no** se usa como evidencia — antes se aceptaba cualquier página que respondiera, sin importar el tema. No prueba que el dato concreto esté en la página (haría falta NLP/extracción real, `EMPRESA_AI_NUEVO_TODO_EVIDENCE.md` §11/§16, sigue sin implementarse), solo descarta el caso burdo de una fuente accesible pero ajena al tema. Cubierto por `ClaimRelevanceCheckerTest` (7 casos) y por los tests de rechazo en `EvidenceAcquisitionServiceTest`.

**Cadena completa verificada en vivo con datos 100% reales** (`EVIDENCE_WEB_SEARCH_API_KEY` configurada en `.env` / `docker-compose.yml`, no committeada): `SerperSearchAdapter.search("precios asesoría empresarial para microempresas Colombia", "co", "es", 5)` devolvió 9 resultados reales de Google → se tomó el primero (camaramedellin.com.co) → `EvidenceAcquisitionService.confirmReachable` hizo un fetch real de esa URL → `EvidenceValidationGate.validate(...)` → `valid=true` → `MissionMemoryService.recordEvidence(...)` persistió el nodo `Evidence` real en Neo4j, confirmado con Cypher (`(:AgentTask)-[:HAS_EVIDENCE]->(:Evidence)` con `source` = la URL real, `verified=false` como está diseñado). Sin mocks en ningún punto de esta cadena. 56 tests en el proyecto (20 del módulo `evidence`: `SerperSearchAdapterTest`, `WebPageFetcherTest`, `EvidenceAcquisitionServiceTest`).

**Conectado al flujo real de agentes** (`CeoService.executeAgentTask`, tool-calling con Ollama): cada tarea de agente ahora hace hasta dos turnos con Ollama en vez de uno:

1. **Turno de decisión** (`toolDecisionSystemPrompt` + `AgentRuntime.buildTaskSummary` — un prompt corto y separado, sin `format`, con `tools=[search_web_evidence]`): el agente decide si necesita buscar evidencia real. Si sí, responde con `{"name": "search_web_evidence", "arguments": {"query": "..."}}`.
2. Si pidió la herramienta, `CeoService.executeTool` ejecuta `searchEvidence` (búsqueda real) y luego, **antes de devolverle nada al modelo**, llama a `confirmReachable` sobre cada candidato (hasta `CANDIDATES_TO_CONFIRM = 5` — Serper puede devolver hasta 10, no tiene sentido hacer fetch a los 10): el candidato que no responde o no está relacionado con la consulta (ver "Verificación semántica" arriba) se descarta ahí mismo (log `TOOL_CANDIDATE_REJECTED`, sin stacktrace) y nunca llega al modelo. Si los `CANDIDATES_TO_CONFIRM` primeros fallan todos, el turno `tool` recibe `{"advertencia": "..."}` en vez de una lista vacía, para que el modelo no interprete el silencio como licencia para inventar una fuente.
3. **Turno final** (prompt completo de `AgentRuntime.buildPrompt`, con `format: AgentResultSchema.SCHEMA`, sin `tools`): produce el `AgentResult` estructurado, ahora con la evidencia real y ya confirmada (si la pidió y sobrevivió el filtro) en el historial.

**Verificado en vivo de punta a punta tras conectar `confirmReachable`** (misión real completa, `qwen3:8b`, sin mocks): los 5 agentes pidieron la herramienta; `TOOL_CANDIDATE_REJECTED` descartó candidatos reales por redirect (302), error de I/O, certificado TLS inválido (`PKIX path building failed`) y contenido no relacionado (`0/6`, `1/6` términos) — incluyendo un caso real donde `engineering` agotó sus 5 candidatos y los 5 fueron rechazados, cayendo en la rama de advertencia; el agente respondió honestamente `NOT_VALIDATED`/`confidence=0.0` en vez de inventar una fuente. Los demás agentes (`qa`, `sales`, `product`) sí tuvieron candidatos confirmados, y esas URLs (y solo esas, no las rechazadas) quedaron persistidas como nodos `Evidence` reales en Neo4j — confirmado con Cypher (`MATCH (t:AgentTask)-[:HAS_EVIDENCE]->(e:Evidence)`). La misión llegó a `AWAITING_INVESTOR`. Nota de wording: el modelo a veces conserva la descripción exacta de `confirmReachable` (con el ratio de términos) y a veces la reformula en su propia frase, pero siempre sobre una URL que de verdad pasó el filtro — no es una garantía de formato, solo de contenido real.

Dos hallazgos importantes verificados en vivo antes de este diseño, no asumidos:

- **`format` y `tools` no se pueden combinar**: con ambos presentes, el modelo queda forzado a la gramática del schema y no puede emitir una llamada a herramienta — confirmado reproduciendo la petición contra Ollama real (también reproducido con `qwen3:8b`: en vez de solo ignorar la herramienta, **inventó una URL y datos falsos** simulando que ya la había llamado). Por eso son dos turnos, no uno — esto no cambia aunque cambie el modelo del agente. `CeoService.callModel` tiene un guard duro (`rejectFormatCombinedWithTools`, cubierto por `CeoServiceToolFormatGuardTest`): si algún cambio futuro llega a combinar ambos en la misma llamada, lanza `IllegalArgumentException` de inmediato en vez de dejar que el modelo alucine en silencio — hoy nunca se dispara porque los dos turnos reales nunca los combinan, pero queda ahí como red de seguridad si alguien toca este código sin conocer esta historia.
- **El modelo original (`qwen2.5-coder:7b`) no envolvía su respuesta en `<tool_call>...</tool_call>`** como espera la plantilla de Ollama, así que `message.tool_calls` casi nunca venía poblado — `CeoService.detectInlineToolCall` reconoce la llamada igual cuando viene como JSON suelto en `content` (se conserva como red de seguridad, ver más abajo). Tampoco importaba si el turno de decisión incluía el prompt completo con "FORMATO OBLIGATORIO" del `AgentResult` en el mismo turno: el modelo lo ignoraba casi siempre y llenaba esa plantilla directamente (reproducido incluso con `tool_choice: "required"`, que Ollama acepta pero no parece hacer cumplir con este modelo) — por eso el turno de decisión usa un prompt corto y separado (`taskSummary`), no el prompt completo.

`AgentResultSchema.EVIDENCE_ITEM_SCHEMA.sourceType` ahora tiene el mismo `enum` que `EvidenceValidationGate` (bug real encontrado en vivo: sin el enum, el modelo generaba valores como `"academic repository"` o `"blog post"` que el gate rechazaba siempre).

### Modelo de agente: `qwen3:8b` (no `qwen2.5-coder:7b`)

Cambiado tras comparar ambos en vivo, no por ficha técnica. `qwen2.5-coder:7b` funcionaba (4/5 agentes buscaban) pero **solo 2/5 (`sales`/`engineering`) volcaban los resultados reales a su `evidence[]` final** — buscar evidencia y usarla resultaron ser dos capacidades distintas, y ese modelo era inconsistente en la segunda. `qwen3:8b` tiene tool-calling nativo real (`message.tool_calls` sí se puebla; con `qwen2.5-coder` casi nunca) y una corrida real de comparación directa dio **5/5 agentes buscando y 5/5 citando URLs reales** en Neo4j — salto medible, no solo teórico.

`think` (parámetro específico de Ollama para modelos con "modo pensamiento", ver `CeoService.callModel`) se maneja distinto por turno, también verificado en vivo antes de fijarlo así:
- **Turno de decisión → `think: true`**: con pensamiento activado, `qwen3` decide correctamente usar la herramienta incluso cuando el prompt completo (`FORMATO OBLIGATORIO`) compite en el mismo turno — algo que ni `qwen2.5-coder` ni el propio `qwen3` con `think: false` logran de forma confiable (3/3 intentos ignorando la herramienta en ambos casos). Cuesta latencia real (~4x más lento que sin pensamiento) — aceptado deliberadamente: el sistema es asíncrono (Kafka + polling, nadie bloquea esperando síncronamente) y Ollama ya sirve las tareas de agente en serie de todos modos (ver nota de `OLLAMA_NUM_PARALLEL` abajo), así que esta latencia no cambia la naturaleza del sistema, solo alarga un poco la fase `WAITING_AGENT_RESULTS`.
- **Turno final → `think: false`**: aquí no hay ambigüedad de herramienta que decidir, solo llenar el contrato con la evidencia ya en mano — el pensamiento no aporta y solo suma latencia (verificado: mismo resultado honesto, `evidence: []` cuando los resultados no alcanzaban para una cifra concreta, en 3.5s en vez de 14.4s).

Nota de infraestructura encontrada de paso: no hay `OLLAMA_NUM_PARALLEL` configurado explícitamente en el contenedor de Ollama, y con `qwen3:8b` usando ~5.5 GB de los 8 GB de VRAM disponibles, casi con certeza Ollama decide 1 solo slot de inferencia — las 5 tareas de agente ya se sirven en serie dentro de Ollama aunque en Java corran en threads paralelos. No es un problema introducido por este cambio, ya era así antes; solo no estaba documentado.

**Verificado en vivo con una misión real completa usando `qwen3:8b`**: **5 de 5 agentes** (`sales`, `product`, `finance`, `engineering`, `qa`) decidieron llamar a `search_web_evidence`, obtuvieron resultados reales de Serper, y **los 5** citaron URLs reales (no inventadas) en su `evidence[]` final — persistidas como nodos `Evidence` reales en Neo4j vía `MissionMemoryService.recordEvidence`, confirmado con Cypher. La misión llegó a `AWAITING_INVESTOR`. Mejora directa y medida sobre la corrida equivalente con `qwen2.5-coder:7b` (4/5 buscaron, solo 2/5 citaron).

**"Consistencia del modelo al volcar evidencia" — cerrado, subsumido por Evidence Binding**: la mejora de `qwen2.5-coder:7b`→`qwen3:8b` (5/5 citando vs. 2/5) seguía siendo, en el fondo, una apuesta a que el modelo "se portara bien" — una corrida real no es garantía estadística. Con `EvidenceBindingGate` (ver esa sección más abajo) ese riesgo queda cerrado de raíz: si un agente busca y no cita, ya no depende de qué tan disciplinado sea el modelo — el gate lo rechaza determinísticamente y lo obliga a corregir. Este apartado queda como nota histórica de *por qué* se migró de modelo, no como un riesgo sin cubrir.

**Pendiente, no bloqueante**: scoring de evidencia. La verificación semántica léxica (`ClaimRelevanceChecker`) ya está implementada y conectada (ver arriba); lo que sigue pendiente ahí es la extracción/NLP real del dato concreto, no solo del tema. **Evidence Binding** ("buscó pero no citó") también está resuelto — ver esa sección más abajo.

**Hallazgo de infraestructura de paso** (no introducido por este cambio, solo observado): durante la consolidación del CEO (`qwen2.5-coder:14b`) inmediatamente después de una tanda de agentes con `qwen3:8b`, `ollama ps` mostró el modelo de 14B corriendo a `30%/70% CPU/GPU` (VRAM: 7/8 GB usados, GPU al 20% de utilización) — probablemente porque ambos modelos compiten por los mismos 8 GB de VRAM y Ollama no alcanza a descargar `qwen3:8b` antes de que el CEO empiece. La consolidación de esa corrida tardó ~7-8 min en vez de los ~3 min documentados antes. No bloqueante (la misión igual terminó en `AWAITING_INVESTOR`), pero es la explicación más probable si una consolidación se ve inusualmente lenta.

## Command Center web (`app/frontend/`)

Hasta acá la única forma de operar la empresa era `curl`/consola. El usuario pidió una interfaz web como forma **principal** de operar la compañía ("torre de control", no un chatbot en terminal) — la consola queda para debugging (`docker logs`, `docker compose restart`, `curl /actuator/health`). v1 (aprobada explícitamente antes de escribir código, ver plan de esa sesión): **Dashboard + Chat + Agents + Missions + Activity**. Opportunities/Customers/Transactions/Evidence/Decisions (mencionados en el mockup original) quedan fuera de la navegación de v1 — no había endpoints de listado para ellos y se agregaron rondas anteriores; se suman a la SPA en una siguiente ronda si hace falta.

Decisiones de arquitectura acordadas con el usuario antes de implementar:
- **Frontend SPA React+Vite+TS**, servida como estáticos por `company-core` (un solo despliegue, un solo puerto) — no un frontend separado con su propio dominio/CORS.
- **Polling simple** para refrescar datos (`@tanstack/react-query`, `refetchInterval` por query) — sin WebSocket ni Server-Sent Events.
- **Activity derivado de Neo4j, no un `KafkaConsumer` nuevo**: sería el primer consumer de Kafka de este proyecto (hoy 100% productor, `CompanyEventPublisher`); dado que polling simple ya fue la elección para todo lo demás, agregar infraestructura de consumo solo para una lista de actividad reciente no encajaba — `ActivityMemoryService.recent` arma la línea de tiempo con una sola query que UNION-ea `AgentTask`/`Mission`/`Evidence`/`Decision` por sus timestamps ya existentes.

### Endpoints nuevos de solo lectura

- `GET /api/company/missions` (`MissionService.list` → `MissionMemoryService.findAll`): misiones recientes, límite fijo 50 (v1 no pagina).
- `GET /api/company/agents/status` (`MissionMemoryService.latestTaskPerAgent`): para cada `Agent`, su `AgentTask` más reciente por `updatedAt`, en cualquier misión; `status="IDLE"` (y el resto `null`) si nunca tuvo tarea — traducido en Java, no en la query (`OPTIONAL MATCH` sin match trae `latest=null`, y acceder a una propiedad de `null` en Cypher da `null`, no error).
- `GET /api/company/activity` (`ActivityMemoryService.recent`): línea de tiempo derivada, ver arriba.

### Chat Intent Router (`ChatIntentRouter`)

El chat no es `POST /chat → LLM → texto`. Antes de tocar Ollama, un router determinista (regex/keywords — mismo criterio que `ClaimRelevanceChecker`/`EvidenceBindingGate`: nunca "el modelo revisándose a sí mismo" para decidir la ruta) clasifica el mensaje:

1. **Inicio de misión** — el regex `(ejecuta|inicia) MISSION-\d+` que antes vivía en `CompanyController` se movió aquí tal cual.
2. **Decisión** (`aprueba`/`rechaza`/`pide más evidencia` + un `MISSION-<id>` **explícito** en el mensaje) → llama **directo** a `MissionService.recordDecision` — la misma gobernanza que `POST /missions/{id}/decision`, nunca una ruta paralela ni una ejecución "de chat" (así lo pidió el usuario explícitamente). Sin un `MISSION-<id>` explícito no se adivina a qué misión: cae al chat general.
3. **Consulta** (estado de agentes, misiones que necesitan aprobación, oportunidades, LEADs, gasto de la compañía) — la respuesta se arma **100% determinísticamente en Java**, sin pasar por Ollama en absoluto. `QueryIntent.LEADS` resuelve a `OpportunityMemoryService.listLeads()`, formateado por `formatLeads` con el mismo patrón que `OPPORTUNITIES`/`formatOpportunities`.
4. **General** → `CeoService.chat`, sin cambios.

**Por qué las consultas no pasan por el modelo (cambio de diseño en vivo)**: el diseño original (aprobado en el plan) pasaba los datos reales a un nuevo `CeoService.answerGroundedQuery` para que el CEO los "fraseara" en lenguaje natural — mismo principio anti-alucinación del resto del proyecto (nunca dejar que el modelo invente, solo que redacte sobre datos reales). Verificado en vivo antes de dar el intent por terminado: con una lista corta (2 oportunidades, 6 agentes) funcionó bien; pero con 25 misiones reales en `AWAITING_INVESTOR`/`FAILED`, el modelo **subcontó** — dijo "9" y enumeró solo 9, sin inventar ninguna que no existiera, pero omitiendo 16 reales. No fue el problema de payload gigante que se diagnosticó primero (una versión aún anterior serializaba el `MissionResponse` completo con el `message` libre de la consolidación del CEO, hasta 69 KB — eso también se corrigió, recortando a un resumen de 3 campos), sino algo más simple: contar/enumerar una lista es una tarea puramente determinista, y no hay ninguna razón para dejarle ese trabajo a un LLM cuando Java lo hace sin margen de error. `CeoService.answerGroundedQuery` se eliminó (quedaba sin uso); las 4 consultas ahora se formatean con métodos dedicados (`formatAgentStatus`, `formatMissionsNeedingAttention`, `formatOpportunities`, `formatCompanyProfit`) en `ChatIntentRouter`.

Verificado en vivo de punta a punta (Ollama/Neo4j reales, sin mocks): las 4 consultas dieron cifras exactas (25/25 misiones, no 9); "aprueba la misión MISSION-XXX porque..." escrito en el chat real creó un nodo `Decision` real (`Cypher` lo confirmó) y movió la misión a `COMPLETED`, idéntico a pegarle al endpoint dedicado. Cubierto por `ChatIntentRouterTest` (11 casos).

### Frontend: estructura y fallback de rutas

`app/frontend/src/`: `api/client.ts` + `api/types.ts` (tipos a mano reflejando los records Java — sin generación automática, mantener sincronizados), `components/Layout.tsx` (sidebar + badge de salud vía polling de `/actuator/health`), `pages/{Dashboard,Chat,Agents,Missions,MissionDetail,Activity}Page.tsx`, `statusColor.ts` (mapeo de estados reales a 🟢🟡🔴⚪, un solo lugar).

### Identidad persistente de agentes (`Agent.name`/`role`/`personality`)

Hasta acá `Agent.name` en Neo4j duplicaba literalmente el rol (`"Sales"`, `"Finance"`) y `Agent.title` era una etiqueta genérica — los agentes eran roles funcionales, no identidades persistentes. Alcance acordado antes de tocar código: **identidad plana** (sin `RoleVersion`/`AgentVersion`, eso sigue sin código), **personalidad solo UI** (no se inyecta en los prompts de `AgentRuntime`/`CeoService` — el usuario fue explícito: "por ahora solo UI, no tocar prompts"), performance por agente explícitamente diferida ("más adelante").

`CompanyMemoryService.initializeCompanyAndAgents()` ahora siembra `name`/`role`/`personality` reales por agente (Alex/CEO, Sofia/Sales, Max/Finance, Luna/Product, Neo/Engineering, Vera/QA — los primeros 5 nombres son del propio usuario, "Vera" es sugerencia mía) y el `MERGE ... SET ... REMOVE a.title` migra los nodos `Agent` reales existentes **in place** en cada arranque (vía `ApplicationReadyEvent`, ya idempotente) — no hizo falta ningún script de migración aparte; verificado en vivo contra el Neo4j real: los 6 agentes existentes quedaron con `title=NULL` y los 3 campos nuevos poblados.

Deliberadamente **no** se tocó: la relación `(:Agent)-[:ASSIGNED_TASK]->(:AgentTask)` (el usuario sugirió renombrarla a `EXECUTES`; ya está en uso/testeada, renombrarla sería puro churn) ni el esquema de `Agent.id` (`"sales"`, no `"AGENT-SALES-001"` como sugería el ejemplo del usuario — se usa en Cypher por todo el proyecto, y su preocupación real era el nombre inventado, no el formato del id). Tampoco se persistió un `model` por agente en Neo4j: hoy es config compartida (`ollama.agent-model`), persistirlo en el grafo lo duplicaría con riesgo de desincronización si algún día varía por agente.

**Bug real encontrado después de dar la ronda por cerrada, ya corregido**: guardar la identidad en Neo4j no alcanzaba — `CeoService.systemPrompt()` (el prompt base compartido por `chat()`, `executeMission` y `executeAgentTask`) nunca le decía al modelo su propio nombre, así que cuando se le preguntaba "¿quién sos?" en el chat real, el CEO (`qwen2.5-coder:14b`) lo inventaba cada vez ("Jack", luego un placeholder literal `"[Nombre del CEO]"`) — el problema exacto que esta feature debía cerrar, pero solo se cerró en la UI/API, no en la conversación real con el modelo. Fix: `systemPrompt()` **no** se tocó (es compartido con la ejecución de los 5 agentes delegados — inyectarle "tu nombre es Alex" ahí habría hecho que `sales`/`finance`/etc. también se creyeran "Alex"). En cambio, `CeoService.chat(...)` arma su propio system message agregando dos líneas aparte, solo para esa llamada: el nombre real ("Tu nombre real es {ceoName}...") y el roster real del equipo ("Este es tu equipo real (nombre y rol)..."). `ChatIntentRouter` (ahora con `CompanyMemoryService` inyectado) resuelve ambos vía los nuevos `CompanyMemoryService.agentName("ceo")` y `CompanyMemoryService.teamRosterDescription()` antes de llamar a `ceoService.chat(...)` — nunca los hardcodea. Verificado en vivo: 3 preguntas distintas sobre su identidad ("¿quién sos?", "cuál es tu nombre", "decime tu nombre exactamente") dieron "Alex" las 3 veces (antes: nombre distinto o placeholder en cada intento); y "preséntame al equipo por favor" —un segundo bug real encontrado en la misma sesión de pruebas: sin roster inyectado, el CEO había inventado 7 roles genéricos ("Líder de Proyectos", "Especialistas en Datos"...) que no existen en la empresa— pasó a listar los 6 agentes reales (Alex/Neo/Max/Luna/Vera/Sofia) con sus roles reales de Neo4j.

**Herramienta `query_company_memory` en el chat (Neo4j como fuente de verdad, no solo hechos pre-inyectados)**: el nombre + roster inyectados arriba cierran esos dos huecos puntuales, pero el problema de fondo seguía abierto — cualquier otra pregunta sobre la empresa que no viniera pre-inyectada en el prompt (cuántas misiones hay, cuál es la utilidad real, qué oportunidades existen) seguía sin ninguna fuente real, y el CEO la alucinaba. En vez de seguir parchando el prompt a mano cada vez que se encuentra un hueco nuevo, `CeoService.chat` ahora hace tool-calling real (mismo patrón de dos turnos que `search_web_evidence` en `executeAgentTask`, pero un tool distinto y exclusivo del chat): turno 1 con la herramienta `query_company_memory` disponible (`topic` restringido a un `enum` fijo — `AGENT_STATUS`/`MISSIONS_NEEDING_ATTENTION`/`OPPORTUNITIES`/`COMPANY_PROFIT` — **nunca** Cypher libre, mismo criterio de todo el proyecto de no exponerle al modelo un canal de consulta arbitraria); si pide la herramienta, se resuelve contra Neo4j y se hace un turno final con el resultado real ya en la conversación. A diferencia del tool-calling de agentes, aquí no hace falta un prompt de decisión corto y separado ni gestionar `format`: el chat nunca usa `format`, así que el mismo turno puede responder directo en texto libre o pedir la herramienta, sin la competencia que forzó ese diseño en `executeAgentTask`.

`CeoService` sigue sin depender de Neo4j directamente (consistente con "es el único cliente de Ollama"): `chat(ceoName, teamRoster, message, companyMemoryQuery)` recibe un `Function<String,String>` que `ChatIntentRouter` provee como `this::answerMemoryTopic` — el mismo método nuevo que ahora también usa el atajo de keywords existente (`handleQuery` delega en él), así que los 4 formatters deterministas (`formatAgentStatus`/etc.) ya escritos y testeados se reusan sin duplicar lógica ni entre el camino rápido (keywords, cero llamadas a Ollama) ni el camino del tool-call.

`parseCompanyMemoryTopic`/`detectInlineCompanyMemoryTopic` en `CeoService` son análogos a los ya existentes `parseStructuredToolCall`/`detectInlineToolCall` de `search_web_evidence` (incluida la misma red de seguridad para `qwen2.5-coder`, que no siempre envuelve la llamada en `message.tool_calls`) pero para el nuevo nombre de herramienta/argumento — deliberadamente no se generalizó un mecanismo común entre ambos: son dos herramientas de dominios distintos (evidencia web vs. memoria empresarial) con call-sites distintos (`executeAgentTask` vs. `chat`), forzar una abstracción compartida ahora sería especular sobre una tercera herramienta que no existe todavía.

Verificado en vivo: preguntando "¿que tan rentable ha sido la empresa hasta ahora?" (frase que no matchea ningún keyword existente) el log confirmó `CEO_CHAT_TOOL_CALL topic=COMPANY_PROFIT`, y el resultado real de la herramienta (`US$0.00` en los 3 campos, confirmado comparando contra la respuesta determinista directa del atajo de keywords) coincidió exactamente — la respuesta narrativa del CEO no citó ninguna cifra falsa, solo parafraseó el hecho real (cero ingresos todavía). Cubierto por un test nuevo en `ChatIntentRouterTest` que captura el `Function` pasado a `ceoService.chat(...)` y confirma que resuelve los 4 topics reales más un topic desconocido. `mvn test` 111/111.

**Bug real encontrado por el usuario y corregido: "preséntame al equipo" caía al chat general en vez de a la ruta determinista.** `detectQuery` solo activaba `AGENT_STATUS` cuando el mensaje contenía `"agente"` **y** (`"trabaj"` o `"estado"`) a la vez — "preséntame al equipo", "¿quién está trabajando ahora?" y "¿qué está haciendo cada agente?" no cumplen esa combinación (ninguna de las tres, confirmado con el `normalize()` real antes de tocar código), así que las tres caían a `ceoService.chat(...)`. Ahí el roster real sí estaba inyectado en el prompt (nombre+rol, sin `status`), pero el modelo (`qwen2.5-coder:14b`) igual **elaboraba por encima** con descripciones de responsabilidades inventadas y, reproducido en vivo por el usuario, agregaba un disclaimer de privacidad contradictorio ("no puedo proporcionar detalles personales...") justo después de listar al equipo — un reflejo de seguridad del modelo tratando a los agentes como si fueran personas reales.

Fix en dos capas:
1. **`detectQuery`** ahora dispara `AGENT_STATUS` con `"equipo"` o `"agente"` o `"trabajando"` solos (ya no exige la combinación) — cubre las tres frases reales del usuario, verificado con las tres contra el chat real: las 3 respondieron en <200ms, con `CHAT_INTENT_QUERY intent=AGENT_STATUS` en el log y **cero** llamadas a Ollama (`grep CEO_CHAT` vacío en esa ventana).
2. **`formatAgentStatus`** ahora antepone un emoji de estado por agente (🟢/🟡/🔴/⚪), con el mismo mapeo semántico que ya usa `statusColor.ts` en el frontend (mismos 3 sets de estados, no una heurística nueva y distinta) — así la respuesta de texto del chat coincide visualmente con lo que ya se ve en Dashboard/Agents.
3. **Defensa adicional en `CeoService.chat`**: una línea nueva en el system prompt aclara explícitamente que los agentes son identidades de software, no personas reales, y que no debe aplicarles privacidad de datos personales — cubre el chat general para frases que ninguna heurística de keywords vaya a anticipar nunca (no reemplaza el fix #1, es la segunda capa).

Cubierto por 3 casos nuevos en `ChatIntentRouterTest` (las tres frases reales del usuario, cada una verificando `verifyNoInteractions(ceoService)`) y 2 assertions actualizadas en el test ya existente de `AGENT_STATUS` (ahora esperan el emoji). `mvn test` 126/126.

### Agent.status ≠ AgentTask.status

**Bug real encontrado por el usuario (con capturas de pantalla) tras el fix anterior**: `AgentStatusResponse.status` era literalmente el `status` de la última `AgentTask` del agente (`PENDING`/`RUNNING`/`COMPLETED`/`FAILED`), nunca un estado propio del agente. Un agente con su última tarea en `COMPLETED` se mostraba como si eso fuera su estado — tanto en el chat ("Neo: COMPLETED") como, confirmado leyendo el código, en la pantalla real **Agents** del frontend (`agent.status === 'IDLE' ? 'Inactivo' : 'Trabajando en: X'` mostraba "Trabajando en: Delivery Feasibility" para un agente que ya había terminado esa tarea).

Alcance acordado con el usuario antes de tocar código (dos preguntas explícitas):
1. **`Agent.status` es una propiedad real y persistida en el nodo `:Agent`** — no un cálculo al vuelo desde la última tarea. "Neo4j es la memoria de la empresa": el estado del agente debe ser un hecho de primera clase en el grafo, consultable directo desde el nodo `Agent`, no algo derivado en cada lectura.
2. **Solo dos valores reales: `WORKING`/`IDLE`**. El usuario proponía originalmente 6 (`ACTIVE`/`WORKING`/`IDLE`/`WAITING`/`ERROR`/`DISABLED`) más un status de tarea `RETRYING` — ninguno de esos 4 adicionales tiene una señal real en el código hoy (los reintentos internos de `AgentRuntime` no cambian `AgentTask.status`, que se queda en `RUNNING`; nada dispara `WAITING`/`DISABLED`), así que no se inventaron solo para llenar el enum — mismo criterio ya aplicado en "Alertas por correo" (6 tipos pedidos, solo 2 con señal real).

`MissionMemoryService.setAgentStatus(agentId, status)` hace `SET a.status=$status` en el nodo `Agent`. `AgentRuntime.executeInternal` llama `memory.setAgentStatus(agentId, "WORKING")` justo después de marcar la tarea `RUNNING`, y `memory.setAgentStatus(agentId, "IDLE")` en un bloque `finally` que envuelve todo el resto del método — así vuelve a `IDLE` sea que la tarea termine en éxito, en `FAILED` tras agotar reintentos, o ante cualquier excepción inesperada; nunca queda "WORKING" para siempre por un camino de error no contemplado.

`AgentStatusResponse` gana el campo `taskStatus` (el status de la última `AgentTask`, ahora explícitamente separado de `status`). `MissionMemoryService.latestTaskPerAgent()` ya no traduce `latest.status` como el status del agente — lee `coalesce(a.status, 'IDLE')` para `status` y `latest.status` para `taskStatus` por separado. `ChatIntentRouter.formatAgentStatus` muestra la tarea en curso si el agente está `WORKING` ("🟢 Sofia (...): WORKING (MISSION-1, MARKET_DISCOVERY)"), o "última tarea + resultado" si está `IDLE` con historial ("⚪ Neo (...): IDLE — última tarea: DELIVERY_FEASIBILITY (MISSION-1), resultado: COMPLETED"). `AgentsPage.tsx` del frontend sigue la misma lógica.

**Migración de los nodos `Agent` ya existentes**: `CompanyMemoryService.initializeCompanyAndAgents()` seedeaba antes `a.status='ACTIVE'` sin condición en cada arranque (valor que ni siquiera es uno de los dos reales ahora) — cambiar el seed a `ON CREATE SET a.status='IDLE'` solo cubre nodos *nuevos*; los 6 agentes reales de esta base (de sesiones anteriores) se quedaron con `status='ACTIVE'` stale, reproducido en vivo (`GET /agents/status` los mostraba `"ACTIVE"` tras el primer redeploy de este fix). Se agregó una normalización idempotente en el mismo `SET`: `a.status = CASE WHEN a.status IN ['WORKING','IDLE'] THEN a.status ELSE 'IDLE' END` — preserva el valor real si ya es `WORKING`/`IDLE` (nunca pisa un `WORKING` legítimo en curso), y corrige cualquier otra cosa a `IDLE`. Verificado en vivo: los 6 agentes pasaron de `"ACTIVE"` a `"IDLE"` en el siguiente restart, sin tocar Neo4j a mano.

**Límite conocido, no resuelto** (documentado, no bloqueante — mismo criterio que el DNS rebinding de `WebPageFetcher`): si el proceso se reinicia con un agente realmente `WORKING` (misión real en curso), no hay reconciliación — el nodo queda en `WORKING` hasta la próxima tarea real de ese agente. No se implementó una solución porque el resto del proyecto tampoco reconcilia estado tras un crash a mitad de misión (p. ej. una misión que quedó en `DELEGATING` para siempre).

Cubierto por 2 casos nuevos en `AgentRuntimeTest` (`WORKING`→`IDLE` en éxito, con `inOrder` verificando la secuencia exacta; `WORKING`→`IDLE` incluso agotando reintentos y terminando en excepción) y 2 casos nuevos en `ChatIntentRouterTest` (formato "última tarea" cuando `IDLE` con historial). `mvn test` 129/129. Verificado en vivo de punta a punta tras redeploy: `GET /agents/status` mostrando `IDLE`+`taskStatus=COMPLETED` para los 6 agentes reales, las tres preguntas del usuario ("¿Quién está trabajando ahora?", "¿Qué está haciendo cada agente?", "¿Qué necesita mi aprobación?") respondiendo con datos 100% reales y `CHAT_INTENT_QUERY` en el log (cero `CEO_CHAT`), y la pantalla real **Agents** del Command Center mostrando "Inactivo — última tarea: ... resultado: COMPLETED" en vez de "Trabajando en...".

### MISSIONS_NEEDING_ATTENTION mezclaba AWAITING_INVESTOR con FAILED bajo "necesitan tu aprobación"

**Bug real encontrado por el usuario probando la pregunta anterior**: con 25 misiones reales acumuladas (15 `AWAITING_INVESTOR` + 10 `FAILED`), "¿Qué necesita mi aprobación?" respondía "Tenés 25 misión(es) que necesitan tu aprobación" listando las 25 — pero una misión `FAILED` no está esperando aprobación. La causa: `formatMissionsNeedingAttention` filtraba deliberadamente `AWAITING_INVESTOR` **o** `FAILED` juntos (diseño original: ambos estados aceptan una decisión real vía `POST /decision`, ver "Decisión del inversionista humano"), pero el texto de respuesta usaba una sola etiqueta ("necesitan tu aprobación") para los dos grupos — precisa para uno, engañosa para el otro.

Alcance acordado con el usuario (dos preguntas explícitas):
1. **Dos consultas deterministas separadas**, no una sola con texto agrupado: `MISSIONS_NEEDING_ATTENTION` pasa a filtrar **estrictamente** `AWAITING_INVESTOR` (el nombre del intent no cambió — solo su filtro — para no romper el keyword routing ni el tool schema existentes); `FAILED_MISSIONS` es un topic/intent nuevo, estrictamente `FAILED`. Cada una 100% precisa sobre su propio estado.
2. **Separar misiones de prueba vs. producción queda para una ronda aparte** — no hay hoy ninguna señal en el código para distinguirlas (ningún campo `environment` en `Mission`), y no se quiso inventar una heurística (p. ej. adivinar por el nombre del id) sin diseñarlo con el usuario primero.

`ChatIntentRouter.detectQuery` chequea `"fallaron"`/`"fallidas"`/`"fallida"` **antes** que las keywords de `MISSIONS_NEEDING_ATTENTION` (no se solapan, pero el orden documenta la intención: la pregunta sobre fallos es más específica). `formatFailedMissions` es análoga a `formatMissionsNeedingAttention` pero sobre `FAILED`, sin el detalle de motivo (solo el listado de ids, mismo nivel de detalle que las otras consultas de este router). El enum `topic` de la herramienta `query_company_memory` en `CeoService` gana `FAILED_MISSIONS`, y la descripción de `MISSIONS_NEEDING_ATTENTION` se corrigió (ya no dice "o fallaron").

Cubierto por: `routesMissionsNeedingAttentionQueryFilteredByStatusWithDeterministicCount` actualizado (ahora una misión `FAILED` en la lista de entrada **no** debe aparecer en la respuesta), `routesFailedMissionsQueryToItsOwnDeterministicFormatting` nuevo, y la nueva rama `FAILED_MISSIONS` en el test del callback de `query_company_memory`. `mvn test` 130/130. Verificado en vivo contra el chat real con los datos reales de 25 misiones: "¿Qué necesita mi aprobación?" → "Tenés 15 misión(es)..." (solo `AWAITING_INVESTOR`); "¿Qué misiones fallaron?" → "Tenés 10 misión(es) fallida(s)..." (solo `FAILED`) — 15+10=25, cuadra exacto con el desglose que el usuario calculó a mano desde la respuesta anterior. Ambas con `CHAT_INTENT_QUERY` en el log, cero `CEO_CHAT`.

### Mission.environment (`PRODUCTION`/`TEST`) — separa actividad empresarial real de misiones de desarrollo

**Bug real encontrado por el usuario, siguiendo inmediatamente al anterior**: incluso con `MISSIONS_NEEDING_ATTENTION` ya filtrando estrictamente `AWAITING_INVESTOR`, las 15 misiones que devolvía seguían siendo casi todas de desarrollo/depuración (`MISSION-DEBUG-007`, `MISSION-STRUCTURED-*`, `MVP-*`, `MISSION-MAIL-TEST-*`, etc.) — el histórico completo de esta conversación probando el proyecto. El chat no tenía forma de distinguir "esto es la empresa real" de "esto es Claude probando una feature".

Alcance acordado con el usuario (dos preguntas explícitas):
1. **`Mission.environment` (`PRODUCTION`/`TEST`) es una propiedad real y persistida** en el nodo `Mission`, nunca una heurística sobre el nombre del `missionId` — `MissionCommand.environment` es opcional en la API (`POST /api/company/missions`); si se omite, `environmentOrDefault()` asume `PRODUCTION` (una misión real por default: quien inicia una misión de prueba debe marcarla `"TEST"` explícitamente). Las misiones iniciadas por chat (`"ejecuta MISSION-XXX"`) también son siempre `PRODUCTION` — es un comando real del fundador.
2. **Todas las consultas empresariales del chat filtran `PRODUCTION` por default**: `MISSIONS_NEEDING_ATTENTION` y `FAILED_MISSIONS` ganan `.filter(m -> "PRODUCTION".equals(m.environment()))`. Nueva consulta `TEST_MISSIONS` (keyword `\bprueba\b` con boundary de palabra — ver bug de abajo) muestra exactamente lo que antes contaminaba las respuestas de negocio, con su propio desglose por status.

**Migración de las ~25 misiones ya existentes**: `find()`/`findAll()` usan `coalesce(m.environment, 'TEST')` al leer — ninguna misión vieja sin el campo necesita una escritura explícita, todas caen a `TEST` por default, que es correcto para el histórico de desarrollo. La única excepción real: **`MISSION-001`** es la misión fundacional real (`docs/MISSION-001.md`, "descubrimiento del primer negocio"), no una prueba — `MissionMemoryService.backfillMissionEnvironment()` (idempotente, llamada desde `CompanyMemoryInitializer` en el mismo `ApplicationReadyEvent` que ya inicializa el resto de la memoria) la marca `PRODUCTION` explícitamente si todavía no tiene el campo. Verificado en vivo con Cypher: `MISSION-001` → `"PRODUCTION"` tras el primer restart con este cambio.

**Bug real encontrado durante la implementación (antes de llegar a Docker)**: el primer intento de keyword para `TEST_MISSIONS` usaba `normalized.contains("prueba")` — pero `"aprueba"` (de `"Aprueba la misión..."`, la palabra que activa `APPROVE`) **contiene** `"prueba"` como substring, así que cualquier decisión de aprobación empezaba a caer incorrectamente en `TEST_MISSIONS`. ### Memoria conversacional del Company Chat (foco de entidades + fallback grounded)

Antes de esta ronda el chat era 100% sin estado: cada `POST /api/company/chat` no tenía forma de resolver una referencia al mensaje anterior. Reportado por el usuario en vivo con el ejemplo real de esta misma sesión: "¿Qué necesita mi aprobación?" listaba misiones, "pero esas están en prueba" no tenía forma de saber qué eran "esas". El usuario fue explícito en cómo NO resolverlo: **"no intentaría arreglarlo con otro prompt del CEO"** — descartando de entrada la opción obvia de pasarle historial de texto crudo al LLM para que "interprete" (spec completo, con las 3 opciones evaluadas y el porqué de la elegida: `docs/superpowers/specs/2026-09-14-conversational-memory-design.md`; plan de implementación: `docs/superpowers/plans/2026-09-14-conversational-memory.md`).

**Diseño implementado** (alcance acordado con el usuario antes de escribir código):
1. **Un solo hilo de conversación global** (`Conversation {id:'MAIN'}`) — no hay concepto de usuario/sesión en esta app, un solo fundador opera todo, así que no se inventa uno.
2. **Persistido en Neo4j**, no en memoria del proceso — mismo criterio que `Agent.status`: "Neo4j es la memoria de la empresa" (palabras del usuario), un hecho real no debe perderse en cada restart del contenedor.
3. **El "foco actual"** (`Conversation.lastMentionedType`/`lastMentionedIds`/`lastMentionedAt`) — qué entidades mencionó la última consulta de listado. Único tipo soportado: `"MISSION"` (el único caso con un pedido concreto; mismo criterio de no inventar generalidad sin uso ya aplicado varias veces en este proyecto). Lo actualizan las 3 consultas que listan misiones: `MISSIONS_NEEDING_ATTENTION`, `FAILED_MISSIONS`, `TEST_MISSIONS`.
4. **Resolución híbrida** (opción C de 3 evaluadas con el usuario): un pronombre demostrativo (`esas`/`esos`/`estas`/`estos`/`ellas`/`ellos`) con predicado reconocido (`prueba`→environment, `fallaron`→FAILED, `aprobacion`/`necesita`→AWAITING_INVESTOR) y foco existente se resuelve consultando el dato **real y actual** de esos `missionId` puntuales (`MissionMemoryService.findByIds`, nuevo) — nunca el texto de la respuesta anterior, que puede estar desactualizado. Sin foco → mensaje determinista de "no tengo claro a qué te referís". Predicado no reconocido → cae al chat general, con el foco expuesto como un topic nuevo (`LAST_MENTIONED`) de `query_company_memory` — grounded, nunca historial crudo.

`ConversationMemoryService` (nuevo, mismo patrón que `MissionMemoryService`/`OpportunityMemoryService`) maneja los nodos `Conversation`/`Message` y el foco. `ChatIntentRouter.route()` ahora envuelve la lógica de siempre (movida a `resolve()`, sin cambio de forma) grabando cada turno completo (mensaje + respuesta final) sin importar qué camino lo resolvió — auditable, mismo criterio que `Decision`/`Evidence`. Índice `RANGE` en `Message.createdAt` desde el día uno: la sesión de profiling de Neo4j que precedió a este diseño (`SHOW INDEXES`/`PROFILE` contra las 4 queries reales del chat) encontró que `latestTaskPerAgent()` ordena en memoria por no tener un índice así — no se repite ese patrón acá, donde el volumen de mensajes crece sin límite natural.

**Dos bugs reales encontrados durante la implementación** (ambos atrapados antes de que el usuario los viera, uno por un test existente, el otro por la verificación en vivo — no por prueba manual sistemática):
1. **`normalize()` saca tildes**: "estás" (verbo) se convertía en "estas" y chocaba con el pronombre demostrativo "estas" — "Hola, ¿cómo estás?" empezaba a interpretarse como una referencia, rompiendo dos tests existentes (`fallsBackToGeneralChatWhenNoIntentMatches`, `passesCompanyMemoryQueryCallbackThatResolvesAllKnownTopics`). Fix: el chequeo de pronombre matchea sobre el texto original con tilde, no el normalizado (`detectReferencePredicate` sí sigue usando `normalize()`, ahí no hay colisión).
2. **El fallback al LLM no tenía ninguna pista de a qué se refería "esas"**: verificado en vivo, una pregunta real ("contame más sobre esas") hizo que el modelo ignorara el foco y alucinara una descripción genérica del equipo en vez de usar `LAST_MENTIONED`. Fix: `handleReference` antepone una nota corta al mensaje que le llega al chat general, aclarando el *tipo* de entidad referenciada (dato que ya se conoce en Java) e instruyendo a usar la herramienta — nunca revela los datos en sí, eso sigue viniendo exclusivamente de `LAST_MENTIONED`. Re-verificado en vivo tras el fix: `CEO_CHAT_TOOL_CALL topic=LAST_MENTIONED` en el log, respuesta con las 36 misiones reales del foco, ninguna inventada.

Cubierto por 6 casos nuevos en `ChatIntentRouterTest` (resolución con foco completo, resolución parcial, sin foco, fallback con la pista verificada, grabación de cada turno sin importar el camino, `TEST_MISSIONS` actualizando el foco). `mvn test` 138/138. `ConversationMemoryService`/`MissionMemoryService.findByIds` sin test directo (integración Neo4j, mismo criterio que el resto de los `*MemoryService`).

**Verificado en vivo de punta a punta, reproduciendo el ejemplo real completo del usuario**: "¿Qué misiones están en prueba?" → 36 reales; "pero esas están en prueba" → *"Correcto. Esas 36 misión(es) pertenecen al entorno de pruebas."* (`CHAT_INTENT_REFERENCE predicate=ENVIRONMENT_TEST focusSize=36` en el log, cero `CEO_CHAT`); "contame más sobre esas" → resumen real con los 36 ids y sus status reales vía `LAST_MENTIONED` (`CEO_CHAT_TOOL_CALL topic=LAST_MENTIONED` en el log). ### El chat no creaba misiones a partir de una instrucción real en lenguaje libre

**Bug real encontrado por el usuario probando la memoria conversacional con una instrucción de negocio real** (una oportunidad de videojuegos, con presupuesto/plazo/objetivo reales, no un mensaje de prueba): `"CEO, inicia una misión para encontrar una oportunidad... No contactes clientes ni gastes dinero sin mi aprobación..."` no creó ninguna misión — el router determinista interpretó la frase **"sin mi aprobación"** (una restricción legítima dentro de la instrucción) como el keyword `aprobacion` de `MISSIONS_NEEDING_ATTENTION`, y respondió con la lista de misiones pendientes de `MISSION-001` en vez de arrancar la misión nueva. Causa raíz: `MISSION_START` solo reconoce el patrón rígido `"ejecuta/inicia MISSION-<número>"` — nunca contempló una instrucción real en lenguaje libre sin un id explícito, así que la frase caía directo a `detectQuery`.

El usuario describió una visión mucho más amplia (capa Command/Query/Strategy, registro de `Company Capabilities` para que el CEO no se niegue a hacer algo que sí puede hacer — ej. dijo "no puedo enviar correos" cuando `AlertMailService` ya existe, solo que no está expuesto como acción del chat — y estructurar la instrucción en un JSON con `budgetLimitUsd`/`deadlineDays`/etc.) pero priorizó explícitamente el fix concreto: *"Primero haría que 'Inicia una misión…' realmente cree y ejecute una misión nueva"*. Esta ronda se limitó a eso — el resto (Capabilities registry, capa Command/Query/Strategy, `SEND_PROGRESS_EMAIL` desde el chat) queda documentado como visión, no descartado, pendiente de una ronda de diseño propia cuando haya un pedido concreto (mismo criterio de todo este proyecto).

**Por qué no hizo falta parsear la instrucción a una estructura rígida**: `MissionExecutor`/`AgentRuntime` ya reciben `instruction` como texto libre para *cualquier* misión (incluso las creadas vía `POST /api/company/missions` con curl) — los agentes trabajan directamente sobre ese texto, no sobre un JSON estructurado. Así que el fix es puramente de *routing*: reconocer que el mensaje es una instrucción de arranque de misión (no una consulta) y pasarle el texto completo, tal cual, a `missionService.start(...)` — sin inventar un parser de presupuesto/plazo/dominio que el resto del sistema no necesita todavía.

`ChatIntentRouter.detectFreeMissionStart` (mensaje normalizado contiene `"mision"` + algún verbo de arranque: `inicia`/`iniciar`/`comienza`/`empieza`/`crea`/`lanza`/`arranca`) corre **antes** que `detectDecision`/`detectQuery` — mismo criterio que ya se aplicó con `TEST_MISSIONS` vs. `APPROVE` (`\bprueba` dentro de `aprueba`): la detección de una acción nueva tiene que ganarle a cualquier keyword de consulta que la instrucción real pueda contener incidentalmente. El id se genera con un timestamp (`"MISSION-" + Instant.now().toEpochMilli()`) — acordado con el usuario explícitamente por simplicidad y cero riesgo de colisión, en vez de un slug legible del contenido (que hubiera necesitado lógica de slugificación que hoy no existe en el proyecto). La misión nueva también actualiza el foco conversacional (`conversationMemory.setLastMentioned("MISSION", List.of(missionId))`) — para que un "¿entendiste la misión?" inmediatamente después tenga, al menos, la misión correcta en foco (aunque el reconocimiento de "la misión" sin pronombre demostrativo explícito sigue sin implementarse — el usuario planea probarlo como paso siguiente, no se adelantó una solución sin verificar primero si hace falta).

Cubierto por `routesFreeFormMissionDescriptionToMissionServiceWithAGeneratedId` (usa deliberadamente una instrucción con la frase real "sin mi aprobación" para probar exactamente la colisión reportada). `mvn test` 139/139. Verificado en vivo con el mensaje real completo del usuario (instrucción de videojuegos, ~500 caracteres): `CHAT_INTENT_FREE_MISSION_START missionId=MISSION-1789435552283` en el log, misión delegada a los 5 agentes reales con el objetivo real (no un stub), confirmado en el log completo de arranque (`PLANNING` → `DELEGATING` → 5 tareas creadas).

### Alertas por correo (`empresa.md` §18)

`empresa.md` exige alertas inmediatas por correo para 6 tipos de evento (bloqueo, fallo crítico, decisión estratégica, riesgo importante, límite de presupuesto, incidente grave) y las manda siempre a `dapine@gmail.com` — hasta esta ronda, sin ningún código detrás. Alcance acordado con el usuario antes de implementar: de los 6, hoy solo se dispara para los **2 con señal clara y ya manejada explícitamente en el código** — misión que llega a `AWAITING_INVESTOR` ("decisión estratégica") y misión que termina en `FAILED` ("fallo crítico"). Los otros 4 no tienen todavía una señal determinista en ningún flujo (no se inventó una heurística nueva solo para cubrir el checklist).

`AlertMailService` (`service/AlertMailService.java`) usa `spring-boot-starter-mail`. El transporte SMTP (host/puerto) sigue siendo config genérica por env vars (`MAIL_HOST`/`MAIL_PORT`, default `smtp.gmail.com:587`, para que el bean `JavaMailSenderImpl` siempre exista — Spring Boot solo autoconfigura ese bean si `spring.mail.host` está presente). Las **credenciales de la cuenta no** (ver más abajo por qué se movieron a Neo4j a mitad de esta ronda, tras aclarar el pedido con el usuario): `send(subject, body)` inyecta `JavaMailSenderImpl` concreto (no la interfaz `JavaMailSender`) y en cada envío llama `setUsername`/`setPassword` con el valor más reciente de `CompanyMemoryService.systemEmail()`/`mailPassword()` antes de mandar — así un cambio hecho desde el Command Center web aplica al siguiente envío sin reiniciar el proceso. Si `systemEmail`/`mailPassword` están vacíos (nunca configurados), ni siquiera intenta enviar. `send` **nunca lanza**: cualquier fallo (cuenta sin configurar, credenciales inválidas, red caída) se loguea como `WARN` y no interrumpe el flujo de misiones — un problema de correo no debe tumbar una misión real. El método es `synchronized` porque `mailSender` es un bean singleton mutable (`setUsername`/`setPassword` antes de cada `send`) — sin eso, dos misiones avanzando en paralelo en el pool de 2 hilos de `missionOrchestratorExecutor` podrían pisarse las credenciales entre sí.

Se llama desde el único punto que ya centraliza las transiciones de estado, `MissionExecutor.advanceMission` (el mismo que persiste en Neo4j y publica a Kafka en una sola operación): si `status` es `AWAITING_INVESTOR` o `FAILED`, dispara el correo correspondiente después de la persistencia/publicación normal, sin tocar la máquina de estados.

**Dos cuentas de correo distintas, no una**: `Company.alertEmail` (a quién le llegan las alertas, seed `dapine@gmail.com` vía `ON CREATE`) y `Company.systemEmail`/`Company.mailPassword` (la cuenta y App Password *propias* que la empresa usa para *enviar*, seed vacío) — el pedido explícito del usuario fue poder "asignarle un correo propio al sistema", no reusar `dapine@gmail.com` como remitente. `mailPassword` se guarda en texto plano en esta misma instancia de Neo4j — **compartida con otros proyectos de esta máquina** (ver "Memoria: Neo4j"); decisión acordada con el usuario para el alcance de MVP (un solo operador, máquina de desarrollo propia), no una recomendación general. `SettingsResponse` nunca incluye `mailPassword`, solo se escribe.

Ambos son editables desde el Command Center web: `GET`/`PUT /api/company/settings` (`CompanyController`, `SettingsCommand`/`SettingsResponse`) y `SettingsPage.tsx` (ruta `/settings`, agregada a `App.tsx`, `Layout.tsx` y a la lista explícita de `SpaController`). `systemEmail`/`mailPassword` son opcionales en `SettingsCommand` y solo se actualizan si vienen no vacíos — así se puede cambiar `alertEmail` sin tener que retipear la clave del sistema cada vez; el frontend deja el campo de clave siempre vacío al cargar (write-only, nunca se rellena con lo guardado).

### El chat podía consultar pero no operar: comandos de gobernanza sobre el foco conversacional

**Bug real encontrado por el usuario probando en vivo** — el escenario exacto que expuso el hueco: "¿Qué misiones requieren mi aprobación?" listó correctamente 2 misiones reales; "Las dos misiones están aprobadas" no aprobó nada (el mensaje no matcheaba ningún camino del router: sin `MISSION-<id>` explícito no entra a `detectDecision`, y "las dos" no es ninguno de los pronombres de `REFERENCE_PRONOUN`, así que ni siquiera entraba a `handleReference` — caía a `detectQuery`/chat general). El usuario lo describió con precisión: *"hasta que esta conversación básica deje de 'hablar' y empiece realmente a operar la empresa"*, y pidió pausar explícitamente cualquier otro trabajo (correo, pagos, customer discovery, más queries, más paneles) hasta cerrar esto — exigiendo una "prueba definitiva" reproducible de punta a punta antes de seguir.

**Diseño**: extensión directa de la memoria conversacional ya existente (ver "Resolución híbrida" más arriba), no un subsistema nuevo. `handleReference` ahora chequea primero si el mensaje es un **comando** de gobernanza (`detectReferenceCommand`, nuevo) antes de chequear si es una **consulta** (`detectReferencePredicate`, existente) — un comando y una consulta nunca son ambiguos entre sí en el mismo mensaje. Si es un comando, `handleReferenceCommand` itera sobre los ids del foco (`ConversationMemoryService.lastMentioned()`) y llama, una por una, a `MissionService.recordDecision` — la **misma** gobernanza real que `POST /missions/{id}/decision` y que el flujo existente de "aprueba MISSION-X" con id explícito; nunca se le pide al LLM que "interprete" el comando, el router ya resolvió qué decisión es y sobre qué misiones aplica antes de tocar Ollama.

**Dos patrones nuevos, deliberadamente separados de `APPROVE`/`REJECT`** (que son formas verbales — "aprueba"/"apruebo" — y exigen un `MISSION-<id>` explícito vía `detectDecision`): `COMMAND_APPROVE`/`COMMAND_REJECT` reconocen las formas **adjetivas** de la decisión (`aprobad[oa]s?`, `rechazad[oa]s?`) que aparecen en un comando sobre el foco ("están **aprobadas**", "queda **rechazada**") — un comando conversacional nunca trae un id de misión en el texto, así que no tiene sentido reusar los patrones que dependen de uno.

**Gate de entrada ampliado**: `REFERENCE_PRONOUN` (`esas`/`esos`/`estas`/`estos`/`ellas`/`ellos`) no alcanza para la frase real del usuario — "las dos misiones están aprobadas" no contiene ningún pronombre demostrativo de esa lista. Se agregó `FOCUS_QUANTIFIER` (`las dos`/`los dos`/`ambas`/`ambos`/`todas`/`todos`) como una segunda condición de entrada a `handleReference` en `resolve()`, deliberadamente separada de `REFERENCE_PRONOUN` en vez de ensancharla — son dos fenómenos gramaticales distintos (pronombre demostrativo vs. cuantificador) y mezclarlos habría arriesgado falsos positivos sobre "esta"/"ese" sueltos, ya evitados a propósito en `REFERENCE_PRONOUN` (ver el comentario existente sobre "estás" vs. "estas"). El pronombre singular "esa" (como en "esa misión queda rechazada") sigue **fuera de alcance en v1** — igual que el resto del conjunto de `REFERENCE_PRONOUN`, que es deliberadamente solo plural.

**Reporte por misión, no todo-o-nada**: si una misión del foco no está en un estado que admita la decisión (`MissionService.recordDecision` lanza `IllegalStateException` — p. ej. ya fue decidida antes), esa falla no debe ocultar el éxito de las demás. `handleReferenceCommand` captura la excepción por misión y arma la respuesta con ✅/❌ individuales (`"✅ MISSION-1 aprobada. ❌ MISSION-2 no se pudo procesar (...)."`), agregando la línea de cierre "Las decisiones fueron registradas en Company Memory." solo si al menos una tuvo éxito.

Cubierto por 3 casos nuevos en `ChatIntentRouterTest` (aprobación de ambas misiones del foco con `verifyNoInteractions(ceoService)` probando que es 100% determinista, resultado parcial cuando una misión falla, y rechazo con el pronombre plural "esas"). `mvn test` 142/142.

### El chat general no tenía memoria real de la charla (solo del foco de misiones)

**Bug real encontrado por el usuario probando en vivo**: "no está recordando las charlas que tengo con el CEO". Reproducido de inmediato: `"Recordá que mi color favorito es el verde"` seguido de `"¿Cuál es mi color favorito?"` → *"Lo siento, pero no tengo acceso a información personal sobre ti..."*. Causa raíz confirmada en código: `CeoService.chat` arma su lista de `messages` para Ollama con **solo** el system prompt y el mensaje del turno actual — nunca los turnos anteriores. `ConversationMemoryService` sí graba cada turno (`Message {role, content, createdAt}`, vía `recordMessage`, ya desde la ronda de "Memoria conversacional" más arriba) pero esos mensajes **nunca se volvían a leer** — la única lectura que existía era `lastMentioned()` (el "foco" de qué misiones se mencionaron), que resuelve referencias tipo "esas"/"las dos" pero no tiene nada que ver con recordar el contenido real de la charla.

Esto es un fenómeno distinto del "foco conversacional" (ver más arriba): el foco resuelve *qué entidades* se mencionaron para comandos/consultas determinísticas; esto es la continuidad de charla libre que cualquier chat con memoria real necesita, y que nunca se había implementado — la sección de "Memoria conversacional" original solo cerró el caso de referencias a misiones, no charla general.

**Diseño**: `ConversationMemoryService.recentMessages(int limit)` (nuevo) lee los últimos `limit` nodos `Message` de `Conversation {id:'MAIN'}` (`ORDER BY m.createdAt DESC LIMIT $limit`, invertido en Java a orden cronológico) y los devuelve como `List<ConversationTurn>` (`model/ConversationTurn.java`, nuevo record `(role, content)` — deliberadamente en `model`, no atado a Neo4j, para que `CeoService` lo reciba sin depender del driver, mismo criterio que el resto del proyecto: "CeoService es el único cliente de Ollama"). `CeoService.chat` gana un parámetro `List<ConversationTurn> history`, insertado entre el mensaje `system` y el mensaje `user` del turno actual vía el nuevo helper `buildHistoryMessages` (mapea `role="ceo"` → `"assistant"`, el rol que espera Ollama — `"ceo"` es el rol que graba `ChatIntentRouter.route`, Ollama no lo conoce). `ChatIntentRouter` pasa `conversationMemory.recentMessages(HISTORY_LIMIT)` en los dos call-sites que caen al chat general (el fallback de `resolve()` y el fallback con pista de `handleReference`) — nunca en los caminos 100% determinísticos (decisión/comando/consulta), que no tocan Ollama.

`HISTORY_LIMIT = 20` (10 turnos): elegido como un límite fijo simple, no configurable — suficiente para continuidad real de una charla sin dejar crecer el prompt del CEO sin límite en una sesión larga. No se implementó resumen/compactación de historial viejo (YAGNI hasta que haya una sesión real lo bastante larga como para que importe).

Cubierto por `CeoServiceChatHistoryTest` (3 casos, sobre el helper puro `buildHistoryMessages`: mapeo de roles, orden cronológico preservado, lista vacía) y un caso nuevo en `ChatIntentRouterTest` (`passesRealConversationHistoryToGeneralChatSoTheCeoRemembersPriorTurns`, verifica que el historial real de `conversationMemory.recentMessages` llega tal cual a `ceoService.chat`). `mvn test` 146/146. `ConversationMemoryService.recentMessages` sin test directo (integración Neo4j, mismo criterio que el resto de los `*MemoryService`).

**Verificado en vivo reproduciendo el reporte exacto del usuario**: con el fix desplegado, repetir `"¿Cuál es mi color favorito?"` (con `"Recordá que mi color favorito es el verde"` ya persistido como turno anterior) devolvió *"Tu color favorito es el verde, Alexander."* — la respuesta exacta que antes fallaba.

**Incidente operativo durante la verificación, no relacionado con el bug en sí**: reconstruir y reiniciar el contenedor para desplegar este fix interrumpió una misión real que el usuario ya tenía corriendo en paralelo (`MissionExecutor` orquesta en threads en memoria del proceso — no sobrevive a un restart, y el proyecto no tiene reconciliación automática para este caso, ver "Límite conocido, no resuelto" en "Agent.status ≠ AgentTask.status" más arriba). La misión quedó con 2/5 agentes completados (`finance`, `product`) y 3 colgados en `RUNNING` para siempre. Se corrigió a mano por Cypher (`status='FAILED'` en la misión y en las 3 tareas colgadas — sin pasar por `MissionMemoryService.updateMission`, así que no se publicó ningún evento Kafka para esta corrección administrativa, deliberado) y se relanzó la misma instrucción real tal cual vía chat como una misión nueva. Lección operativa, no de código: antes de reconstruir/reiniciar el contenedor, confirmar que no haya una misión real en curso.

### "dame un status" hacía que el CEO inventara un resumen completo (placeholders sin rellenar)

**Bug real y grave encontrado por el usuario probando en vivo, con evidencia textual inequívoca**: `"dame un status"` no matcheaba ningún keyword determinístico existente (`AGENT_STATUS`/`MISSIONS_NEEDING_ATTENTION`/etc. exigen palabras más específicas — "equipo", "aprobación", "oportunidad"...) y caía al chat general. Sin ninguna herramienta que le diera un resumen agregado real, el CEO (LLM) alucinó un informe completo: inventó `"MISSION-1789442779162: En curso"` (una misión real, pero con un status que no es ninguno de los reales del enum), afirmó `"Se encontraron 5 oportunidades"` sin verificarlo, y — la señal más clara de todas — dejó literalmente sin rellenar los placeholders de la plantilla que estaba completando: `[Nombre del cliente]`, `[Problema específico]`, `[Precio]`, `[Costo]`. El usuario lo diagnosticó con precisión: *"esto ya no es un problema de UI, es un problema de arquitectura del Company Chat"* — un status de empresa no puede pasar primero por el LLM para que él "reconstruya" el estado; debe ser Neo4j → Java → el CEO solo redacta sobre datos ya resueltos.

**Diseño** (siguiendo exactamente el criterio que ya rige las otras 6 consultas de este router: contar/enumerar es una tarea determinista, nunca se le delega al modelo): nuevo `QueryIntent.COMPANY_STATUS`, con su propio formatter `formatCompanyStatus()` que arma un snapshot agregado 100% real — capital semilla (`AppProperties.seedCapitalUsd`, nuevo — `ChatIntentRouter` ahora lo recibe inyectado), agentes trabajando/inactivos (`missionMemory.latestTaskPerAgent()`, ya existente), misiones activas/esperando aprobación/fallidas — **filtradas a `environment=PRODUCTION`**, mismo criterio que `MISSIONS_NEEDING_ATTENTION`/`FAILED_MISSIONS` (`missionMemory.findAll(50)`, ya existente), oportunidades registradas (`OpportunityMemoryService.countOpportunities()`, nuevo — un conteo real, no la lista capada de `listRecent`), prospectos/leads y clientes reales (`CustomerMemoryService.countCustomersAndProspects()`, nuevo — distingue un `Customer` real, sin `status` seteado por `registerCustomer`, de un candidato LEAD de agente, que siempre tiene `status='LEAD'`: un candidato de agente es una hipótesis, nunca se debe contar como cliente real), e ingresos/beneficio neto (`customerMemory.companyWideTotalRevenueAndCost()`, ya existente). Cada número sale de una consulta real; el CEO nunca lo completa, solo lo redacta cuando pasa por la herramienta `query_company_memory` (`COMPANY_STATUS` agregado a su enum de topics).

**Gate de entrada**: keyword `"status"` (y alternativas en español: "estado general"/"estado actual"/"estado de forjai"/"estado de la empresa"), chequeado **al final** de `detectQuery` — deliberado: si el mensaje ya contiene una palabra más específica ("agente", "oportunidad", etc.), esa consulta más precisa gana primero; `COMPANY_STATUS` es el catch-all para un pedido genérico de resumen que no encaja en ninguna consulta puntual.

**Defensa adicional en el system prompt de `CeoService.chat`** (además del fix determinístico, no en su lugar — regla explícita pedida por el usuario: *"El CEO no puede afirmar que un dato existe si no viene de Company Memory"*): una línea nueva prohíbe explícitamente completar con placeholders de plantilla sin rellenar (cita los ejemplos reales vistos: `[Nombre del cliente]`, `[Precio]`, `[Problema específico]`) y exige decir "no tengo ese dato registrado" en vez de inventar. Esta capa cubre frases futuras que ninguna heurística de keywords vaya a anticipar — no reemplaza el fix determinístico, que es la defensa principal.

Cubierto por `routesCompanyStatusQueryToADeterministicAggregateSnapshot` (misiones TEST excluidas del conteo, `verifyNoInteractions(ceoService)` probando que es 100% determinista) y la nueva rama `COMPANY_STATUS` en el test del callback de `query_company_memory`. `mvn test` 147/147.

**Verificado en vivo con la prueba de aceptación exacta que propuso el usuario** (`"Dame un status exacto de Forjai. No me des estimaciones ni supongas información. Usa únicamente datos registrados en Company Memory."`): respuesta idéntica byte a byte a la de `"dame un status"` simple (ambas activan `COMPANY_STATUS` por keyword) — *"Estado actual de Forjai: capital disponible US$50.00. Agentes: 0 trabajando, 6 inactivo(s). Misiones (producción): 0 activa(s), 2 esperando tu aprobación, 1 fallida(s). Oportunidades registradas: 2. Prospectos (leads): 20. Clientes reales: 0. Ingresos: US$0.00. Beneficio neto: US$0.00."* — sin ningún placeholder, sin ninguna cifra inventada. `CHAT_INTENT_QUERY intent=COMPANY_STATUS` en el log, cero `CEO_CHAT`. **Fuera de alcance de esta ronda, a propósito**: de las 8 consultas que propuso el usuario, ya existían 4 bajo otro nombre (`GET_AGENTS_STATUS`≈`AGENT_STATUS`, `GET_PENDING_APPROVALS`≈`MISSIONS_NEEDING_ATTENTION`, `GET_OPPORTUNITIES`≈`OPPORTUNITIES`, `GET_FINANCIAL_STATUS`≈`COMPANY_PROFIT`) y esta ronda cerró la pieza que estaba realmente rota (`GET_COMPANY_STATUS`). `GET_ACTIVE_MISSIONS` (listado de misiones activas con su status exacto, no solo el conteo agregado) y `GET_RECENT_ACTIVITY` desde el chat (`ActivityMemoryService.recent` ya existe y alimenta la pantalla Activity del Command Center, pero no está expuesta como topic de chat) quedan pendientes de un pedido concreto — mismo criterio de todo este proyecto.

### "¿Cómo va MISSION-X?" caía al chat general y el CEO decía "no tengo acceso"

**Bug real reportado por el usuario, con el mismo diagnóstico de fondo que "dame un status" arriba**: `MissionService.details(missionId)` ya existe y respalda `GET /api/company/missions/{missionId}/details` con el dato real (status, progreso, paso actual, tareas de cada agente), pero ningún camino del chat lo consultaba — "¿cómo va MISSION-X?"/"dame los avances de MISSION-X"/"¿qué está haciendo MISSION-X?" no matcheaban ningún `QueryIntent` existente y caían al chat general, donde el CEO respondía que no tenía acceso a esa información.

**Diseño**: a diferencia de las demás consultas de este router (todas agregados sin parámetros), esta necesita un `missionId` — por eso no se sumó como un valor más de `QueryIntent`, sino como un chequeo propio, `resolveMissionDetailsQuery(message) -> Optional<String>`, corrido en `resolve()` justo después de `detectDecision` (mismo lugar lógico: ambos extraen un `MISSION-<id>` explícito con el mismo patrón `MISSION_ID`). Si el mensaje trae un `MISSION-<id>` explícito, se usa directo; si no, pero menciona "la misión" (sin id) con alguna de las palabras clave (`"como va"`, `"avance"`, `"progreso"`, `"detalles"`, `"que esta haciendo"`), se resuelve contra el foco conversacional (`conversationMemory.lastMentioned()`) solo si hay exactamente una misión en foco — mismo criterio que `detectDecision`: sin un id explícito y sin foco inequívoco, nunca se adivina, cae al chat general. `handleMissionDetailsQuery` llama a `missionService.details(missionId)` y formatea la respuesta 100% en Java (`formatMissionDetails`) — nunca pasa por el CEO, mismo criterio de todo el router (contar/enumerar/reportar un estado real es determinista, delegarlo al modelo ya causó alucinación en el pasado, ver "dame un status" arriba).

**Cuidado con colisión de keywords**: `"que esta haciendo"` se superpone a propósito con la frase que ya dispara `AGENT_STATUS` ("¿Qué está haciendo cada agente?") — se resuelve exigiendo que el mensaje mencione una misión (id explícito o la palabra "mision") para que `resolveMissionDetailsQuery` devuelva algo; sin eso, cae limpio a `detectQuery`/`AGENT_STATUS` como antes. Cubierto explícitamente por un test de regresión sobre el mensaje exacto que ya prueba `AGENT_STATUS`.

Cubierto por 4 casos nuevos en `ChatIntentRouterTest`: id explícito, resolución vía foco conversacional sin id, misión no encontrada, y fallback al chat general sin id ni foco. `mvn test` 151/151.

**Fuera de alcance de esta ronda, a propósito**: extender la herramienta `query_company_memory` de `CeoService` para que el chat general (no solo el atajo determinista de keywords) también pueda pedir el detalle de una misión puntual — hoy esa herramienta solo soporta topics sin parámetros; agregarle un `missionId` opcional es un cambio de esquema más grande, pendiente de que haga falta en la práctica.

### Chat con prospectos reales por misión, y calidad de esos prospectos (`confidence`, `resolveOpportunityForMissionQuery`, `resolveCustomerReference`)

**Bug real reportado por el usuario probando en vivo**: preguntar *"¿qué oportunidades concretas tenemos en la misión MISSION-X y qué prospectos reales están asociados a cada una?"* devolvía el párrafo completo de la instrucción de la misión (`Opportunity.description`) y **ningún** prospecto, pese a que la misión sí generó `Customer{status:'LEAD'}` reales, verificados a mano con Cypher. Un follow-up ("contactalo") hacía que el CEO respondiera que no tiene acceso a datos personales — nunca intentaba buscarlos en Neo4j, donde sí existen. Un segundo hallazgo, en la misma sesión de pruebas: los prospectos que generaban los agentes tenían nombres que sonaban a empresas (`"Studio PixelCraft"`, `"GameForge Studios"`) pero su evidencia citaba un artículo genérico de tendencias del sector, no la página de esa empresa puntual — segmentos de mercado con nombre, no empresas verificadas y ubicables.

**Diseño (dos rondas, misma sesión de brainstorming arquitectural)**:

1. **`AgentResult.CustomerCandidate` gana `confidence`** (double, 0.0–1.0, autoreportado por el agente — no calculado por el sistema), campo `required` en `AgentResultSchema` con `minimum`/`maximum` 0–1. `AgentResultValidator` gana `validateCustomerCandidates` (mismo patrón que la validación de `confidence` a nivel de `AgentResult`) — un candidato con `confidence` fuera de rango rechaza la tarea igual que cualquier otro error de validación, con reintento.
2. **`OPPORTUNITIES` con `MISSION-<id>` explícito trae los prospectos reales**, ordenados por `confidence` descendente (`resolveOpportunityForMissionQuery`/`handleOpportunityForMissionQuery`, mismo patrón arquitectónico que `resolveMissionDetailsQuery`: un chequeo propio en `resolve()`, corrido después de `detectDecision`, que solo actúa con un id explícito — sin cambios al comportamiento global sin id). `OpportunityMemoryService.listCandidatesForMission` hace `MATCH (o:Opportunity {missionId})-[:HAS_CANDIDATE]->(c:Customer {status:'LEAD'})`. Esto también setea el foco conversacional `type="CUSTOMER"` con los ids en ese mismo orden.
3. **"contactalo" resuelve contra el foco `CUSTOMER`** (`resolveCustomerReference`/`handleCustomerReference`): si el mensaje menciona el nombre de un prospecto en foco (substring, case-insensitive) resuelve ese; si no y hay varios, resuelve el de mayor `confidence` (primero en la lista) y lo aclara explícitamente; sin foco `CUSTOMER` vigente, cae al chat general. **Nunca inventa un dato de contacto** (teléfono/email) — declara explícitamente que no lo tiene, mismo criterio anti-alucinación del resto del proyecto. El gate de entrada es un `Pattern` nombrado (`CONTACT_REFERENCE = \bcontacta(lo|la|me|los|las)?\b|\bcontacto de\b`), no un `contains("contact")` ingenuo — ver bug abajo.
4. **Especificidad del prompt** (ronda separada, mismo bloque de texto): la instrucción de `customerCandidates` en `AgentRuntime.buildPrompt` ahora exige EMPRESAS CONCRETAS Y NOMBRADAS con fuente específica de esa empresa puntual (nunca un artículo general de la industria), y liga `confidence` a ese mismo criterio (alto >0.7 solo con fuente específica de esa empresa; bajo <0.4 si es más un segmento que una empresa verificable). Sin gate nuevo en código — es una mejora probabilística del prompt, no una garantía dura (no existe forma determinística de validar "esto es una empresa real y específica").

**Dos bugs reales encontrados en la revisión final de rama, antes de llegar a producción** (ninguno visible en las revisiones por tarea — ambos son interacciones entre tareas que solo aparecen mirando la rama completa):

1. **`ORDER BY c.confidence DESC` ordenaba los candidatos legacy (sin `confidence`) PRIMERO, no último** — en Cypher, `null` se considera el valor más alto al ordenar, así que los ~20 `Customer{status:'LEAD'}` ya existentes (creados antes de esta ronda, sin la propiedad `confidence`) se mostraban arriba de todo bajo el encabezado "ordenados por probabilidad", exactamente al revés de la intención. El `coalesce(c.confidence, 0.0)` estaba en el `RETURN` pero no en el `ORDER BY`. Fix: `ORDER BY coalesce(c.confidence, 0.0) DESC`. **Verificado en vivo** contra `MISSION-1789701859658` (7 candidatos legacy reales, todos sin `confidence`): subí manualmente uno a `0.9` por Cypher, confirmé que pasó a aparecer primero tanto en la query cruda como en la respuesta real del chat (`GameForge Studios (confidence=0.90, ...)` como primer resultado), y repuse el dato original después.
2. **El foco `type="CUSTOMER"` (nuevo) rompía los dos consumidores preexistentes del foco conversacional**, que asumían incondicionalmente `type="MISSION"` (nunca tocados por estas tareas, por eso invisibles en review por-tarea): `handleReference` intentaba `missionMemory.findByIds(<ids de customer>)` y devolvía respuestas sin sentido (p. ej. `"No, ninguna de esas 0 misión(es)..."`); `formatLastMentioned` (la herramienta `LAST_MENTIONED` que el CEO puede pedir) devolvía `"Las últimas misiones mencionadas fueron: ."` (string vacío) presentado al CEO como dato fundamentado. Fix: ambos métodos ahora ramifican por `focus.type()` — `handleReference` cae al mismo fallback de hint genérico que ya existía para predicados no reconocidos; `formatLastMentioned` gana una rama `CUSTOMER` que usa `OpportunityMemoryService.findCandidatesByIds` para responder con datos reales.
3. **(Encontrado y corregido en la Task 5, no en la revisión final)**: el gate original de "contactalo" era `normalized.contains("contact")` — interceptaba la consulta global preexistente de LEADs (`"¿qué leads tengo para contactar?"`, que contiene "contact" vía "contactar") cada vez que un foco `CUSTOMER` estaba activo, devolviendo un solo prospecto en vez de la lista completa. Fix: `Pattern` nombrado que excluye el infinitivo "contactar". **Verificado en vivo**: con el foco `CUSTOMER` todavía activo (de la prueba del punto 1), "¿qué leads tengo para contactar?" siguió devolviendo la lista global completa (7 leads), no fue interceptada.

**Verificado en vivo de punta a punta** (Docker real, Neo4j/Ollama reales, sin mocks; `mvn test` 171/171):

### `CompanyTools`: capa única de consultas, con parámetros reales

**Contexto**: el usuario propuso una arquitectura completa de "Company Chat" como interfaz oficial única de Forjai — auditando su propuesta contra el código real, la mayoría ya existía (consultas deterministas, comandos de gobernanza que ejecutan de verdad, foco conversacional). El problema real de arquitectura confirmado leyendo el código: `ChatIntentRouter.answerMemoryTopic(String topic)` ya era un despachador único usado tanto por el atajo de keywords como por la herramienta `query_company_memory` del CEO — pero no soportaba parámetros. Por eso el detalle de una misión o de una oportunidad puntual (`resolveMissionDetailsQuery`/`resolveOpportunityForMissionQuery`) tenía su propio chequeo aparte en `resolve()`, y **nunca quedaba disponible para el chat general del CEO** si la pregunta no matcheaba el keyword exacto — el CEO no tenía forma de pedir ese dato vía herramienta.

**Diseño**: `CompanyTools` (nueva, `com.aicompany.core.service.CompanyTools`) reemplaza el `switch` de `answerMemoryTopic` y los ~13 métodos privados de formateo que antes vivían dentro de `ChatIntentRouter` — 11 métodos tipados (`getCompanyStatus`, `getAgentStatus`, `getPendingApprovals`, `getFailedMissions`, `getTestMissions`, `getOpportunities`, `getOpportunity(missionId)`, `getProspects`, `getFinancialStatus`, `getMission(missionId)`, `getLastMentioned`) más el helper compartido `formatCandidate(LeadResponse)`, todos devolviendo `String` ya formateado en español (mismo criterio anti-alucinación de siempre: contar/formatear es determinista, nunca se le pide al LLM). `ChatIntentRouter` y `CeoService` la consumen por composición. Los comandos de gobernanza (`aprueba`/`rechaza`, "las dos están aprobadas") y la desambiguación de "contactalo" **no** se movieron — siguen en `ChatIntentRouter`, porque necesitan objetos `LeadResponse`/`MissionResponse` crudos para decidir, no texto ya formateado.

La herramienta `query_company_memory` de `CeoService` gana un parámetro `id` opcional y dos topics nuevos, `MISSION_DETAILS`/`OPPORTUNITY_DETAILS`, que reusan exactamente `CompanyTools.getMission(id)`/`getOpportunity(id)` — cierra la brecha real: ahora el chat general del CEO también puede pedir el detalle de una misión u oportunidad puntual, no solo el atajo de keywords. `parseCompanyMemoryTopic`/`detectInlineCompanyMemoryTopic` pasan de `private String` a package-private `CompanyMemoryQuery(topic, id)` (mismo patrón de testabilidad ya usado en el proyecto, ver `SerperSearchAdapter.parseResults`), y `CeoService.chat` recibe ahora un `BiFunction<String, String, String>` en vez de `Function<String, String>`.

**Bug real encontrado en la revisión final de rama, antes de llegar a producción** (invisible en review por-tarea, porque ningún topic anterior tenía un parámetro que pudiera faltar): con `id` deliberadamente no marcado `required` en el schema (9 de los 11 topics nunca lo usan), un tool-call real del modelo puede omitirlo para `MISSION_DETAILS`/`OPPORTUNITY_DETAILS` — y `Map.of("id", null)` (dentro de `MissionMemoryService.find`/`OpportunityMemoryService.findByMissionId`) lanza `NullPointerException` sin capturar, que llega crudo como HTTP 500 (el proyecto no tiene `@ControllerAdvice`) y, como la excepción corta `resolve()` antes de `route()` grabar el turno, la conversación ni siquiera queda registrada. Fix: `answerMemoryTopic` devuelve un mensaje determinista pidiendo el id en vez de llamar a `CompanyTools` cuando `id` viene nulo/vacío — así el mensaje entra como resultado de la herramienta y el CEO puede reintentar, en vez de que la request entera falle. Segundo hallazgo relacionado (menor): el atajo de keywords normaliza el id a mayúsculas antes de llamar a `CompanyTools`, pero el camino del tool-call pasaba el string del modelo tal cual — `CompanyTools.getMission`/`getOpportunity` ahora normalizan (`trim().toUpperCase`) internamente, así la garantía vive en la consulta, no duplicada en cada llamador.

**Verificado en vivo** (Docker real, Neo4j/Ollama reales; `mvn test` 199/199): `dame un status` (`COMPANY_STATUS`), `¿cómo va la misión MISSION-X?` (vía el atajo determinista, `MISSION_DETAILS`), `¿qué tareas tiene asignadas cada agente?` (`AGENT_STATUS`) y `¿qué leads tengo para contactar?` (`LEADS`) — las 4 con datos 100% reales, sin regresión tras la relocación de lógica. **No se pudo confirmar en vivo que el CEO (`qwen2.5-coder:14b`) invoque realmente `MISSION_DETAILS`/`OPPORTUNITY_DETAILS` vía tool-call**: en 2 intentos con preguntas que evitaban deliberadamente los keywords deterministas, el modelo respondió desde su propio razonamiento (una vez inventando una disculpa de "hubo un error" sin haber llamado a la herramienta en absoluto, confirmado por la ausencia de `CEO_CHAT_TOOL_CALL` en el log) en vez de pedir el dato — consistente con la fiabilidad de tool-calling ya documentada de este modelo local (la razón original por la que existe `detectInlineCompanyMemoryTopic` como red de seguridad). El mecanismo está completo y cubierto por test (`CeoServiceCompanyMemoryTopicTest`, `ChatIntentRouterTest`), pero la confirmación en vivo de que el modelo lo usa espontáneamente queda pendiente — podría mejorar si en el futuro el CEO usa un modelo con tool-calling más confiable (ver el spec de NVIDIA, todavía sin implementar).

**Fuera de alcance de esta ronda, a propósito**: un tool-call de `OPPORTUNITY_DETAILS` desde el chat general puede cambiar el foco conversacional de `MISSION` a `CUSTOMER` (mismo efecto secundario que ya tenía el atajo de keywords, ahora también alcanzable desde el chat general) — si el fundador dice después "las dos misiones están aprobadas" con un foco `CUSTOMER` activo, el comando de gobernanza no encuentra misiones y no hace nada. Falla de forma segura (nunca aprueba la misión equivocada, el comando simplemente no dispara), pero es una interacción real entre esta ronda y el "foco único" existente — evaluado y dejado como está, es una decisión de diseño (¿debería el tool-call de solo-lectura evitar tocar el foco?) que le corresponde al fundador, no una que se resolvió unilateralmente acá.

### Consultas nuevas del chat: actividad reciente, decisiones, misiones activas (Sub-proyecto B de "Company Chat completo")

**Contexto**: continuación directa de `CompanyTools` (arriba). `ActivityMemoryService.recent(20)` ya alimentaba la pantalla Activity del Command Center pero el chat no tenía ningún camino para consultarla; los nodos `Decision` reales existían desde "Decisión del inversionista humano" pero nunca se agregó ninguna consulta de listado sobre ellos; y `COMPANY_STATUS` solo traía un **conteo** de misiones activas, nunca un listado con sus ids/status/progreso reales.

**Diseño**: 3 métodos nuevos en `CompanyTools` — `getRecentActivity()` (reusa `ActivityMemoryService.recent(RECENT_ACTIVITY_LIMIT=20)`), `getRecentDecisions()` (nuevo `MissionMemoryService.recentDecisions(RECENT_DECISIONS_LIMIT=10)`, con un modelo nuevo `DecisionActivity(decisionId, missionId, decision, reasoning, decidedAt)` — `DecisionResponse` no sirve porque es la confirmación de escritura de `recordDecision` y no carga `reasoning`), y `getActiveMissions()` (listado, no solo conteo, reusando el mismo criterio `isActiveMission` — extraído como helper privado estático — que ya usa `getCompanyStatus`, para que ambos nunca puedan desincronizarse). `getActiveMissions` también setea el foco conversacional (`type="MISSION"`), mismo criterio que `getPendingApprovals`/`getFailedMissions`/`getTestMissions`; `getRecentDecisions` no, porque un listado histórico no es un conjunto sobre el que tenga sentido "aprobar las dos" después. 3 topics nuevos en `query_company_memory` (`RECENT_ACTIVITY`/`RECENT_DECISIONS`/`ACTIVE_MISSIONS`, ninguno con `id`) y 3 keywords nuevas en `detectQuery` (`"actividad"`, `"decision"` con boundary de palabra, `"mision"+"activa"` juntas).

**6 hallazgos reales de la revisión final de rama, todos corregidos en una sola ronda de fix**:
1. **Colisión de keyword** (Importante): `"decision"` como substring disparaba `RECENT_DECISIONS` incluso en "¿qué misiones necesitan una decisión?" (una pregunta real sobre aprobaciones pendientes, no sobre historial) — mismo patrón de bug recurrente en este proyecto (`\bprueba` vs `aprueba`, `"mision"`+verbo de arranque vs "sin mi aprobación"). Fix: `Pattern.compile("(?i)\\bdecisiones\\b|\\bdecision(es)?\\s+tom")`, reordenado después de `MISSIONS_NEEDING_ATTENTION`/`FAILED_MISSIONS`/`TEST_MISSIONS` para que la consulta más específica de aprobaciones gane primero.
2. **`getRecentDecisions` perdía `decidedAt`** (Importante): con varias decisiones reales sobre la misma misión (un escenario real, ej. `REQUEST_MORE_EVIDENCE` seguido de `APPROVE`), el listado las volvía indistinguibles. Fix: el formato ahora incluye el timestamp.
3. **Predicado de "misión activa" duplicado** (Importante): `getActiveMissions`/`getCompanyStatus` tenían la misma lógica de filtro inline, con solo un comentario evitando que divergieran. Fix: extraído a `private static boolean isActiveMission(MissionResponse m)`, usado por ambos — confirmado en re-revisión que el chequeo de entorno es un no-op inofensivo en `getCompanyStatus` (que ya pre-filtra `PRODUCTION` antes) pero es la única guardia real en `getActiveMissions` (que no pre-filtra).
4. **Nodo `Decision` malformado podía tumbar toda la consulta y ordenarse primero** (Menor): el quirk del driver de Neo4j donde `NullValue.asString()` devuelve el string literal `"null"` (no un null real) hace que `Instant.parse("null")` lance excepción en vez de NPE — y por cómo Neo4j ordena `null` como el valor más grande en `ORDER BY ... DESC`, un nodo así se habría mostrado primero. Fix: `WHERE d.decidedAt IS NOT NULL` en el Cypher de `recentDecisions`.
5. **`reasoning` sin truncar** (Menor): podía tener ~500 caracteres (una instrucción de misión completa). Fix: truncado a 100 caracteres con "...", mismo criterio que ya usa `ActivityMemoryService`.
6. **Números mágicos 20/10** (Menor): extraídos como `RECENT_ACTIVITY_LIMIT`/`RECENT_DECISIONS_LIMIT`.

**Verificado en vivo** (Docker real reconstruido, Neo4j real; `mvn test` 209/209): sembrando directamente en Neo4j 1 misión `PRODUCTION`/`DELEGATING` (activa), 1 misión `PRODUCTION`/`COMPLETED` con una `Decision` real (`APPROVE`, `reasoning` largo para probar el truncado) y 1 `AgentTask` real — `"¿qué actividad reciente hay?"` devolvió los 4 eventos reales (`TASK`/`MISSION`×2/`DECISION`); `"¿qué decisiones tomé?"` devolvió la decisión real con `decidedAt` y el `reasoning` truncado a 100 caracteres; `"¿qué misiones están activas?"` devolvió exactamente la misión `DELEGATING` sembrada. Chequeo de aceptación específico del spec confirmado: `"¿qué misiones están activas?"` → 1 misión, `"dame un status"` → `"1 activa(s)"` — coinciden exacto. Las 4 preguntas con `CHAT_INTENT_QUERY` en el log y **cero** `CEO_CHAT` (100% determinista, sin tocar Ollama). Datos de prueba borrados de Neo4j al terminar.

### CEO en NVIDIA NIM con fallback a Ollama (Sub-proyecto E de "Company Chat completo")

**Contexto**: un spike previo (`superpowers:brainstorming`, path spike) comparó `qwen2.5-coder:14b` (Ollama, CEO actual) contra `openai/gpt-oss-20b` (NVIDIA NIM, endpoint gratuito) con el prompt real de consolidación de una misión real, 3 rondas por proveedor: NVIDIA distinguió hecho/hipótesis en 3/3 rondas (Ollama, 1/3) y citó fuentes reales de la evidencia ya persistida en 3/3 (Ollama, 0/3). Una ronda de NVIDIA falló con `content: null` — causa raíz: `gpt-oss-20b` es un modelo "razonador" que gasta tokens en un `reasoning` oculto antes de responder, y con `max_tokens` insuficiente se queda sin presupuesto para el contenido final (`finish_reason: "length"`); `max_tokens=8192` lo resuelve. Objetivo de esta ronda: que el CEO (chat + consolidación de misión) use NVIDIA NIM como proveedor principal, con fallback automático y auditable a Ollama — los 5 agentes delegados (`sales`/`product`/`finance`/`engineering`/`qa`) **no cambian**, siguen 100% en Ollama local.

**Diseño**: paquete nuevo `com.aicompany.core.llm` con `LlmProvider` (interfaz, `chat(operation, messages, tools) -> LlmResponse`) y dos implementaciones — `OllamaLlmProvider` (extrae la llamada RestClient a Ollama que antes vivía en `CeoService.callModel`, acotada a las llamadas del CEO: nunca `format`/`think`, exclusivos de `executeAgentTask`) y `NvidiaNimLlmProvider` (cliente OpenAI-compatible de `https://integrate.api.nvidia.com/v1/chat/completions`, mismo patrón que `SerperSearchAdapter`: construye su propio `RestClient`, valida la API key al momento de la llamada, no al construirse). `CeoService` recibe el proveedor configurado (`ceoProvider`, `@Qualifier`, seleccionado por Spring según `llm.ceo-provider=ollama|nvidia`, default `ollama` — nadie activa NVIDIA sin querer) más `OllamaLlmProvider` como respaldo fijo, y envuelve las dos únicas llamadas del CEO (`chat`, `executeMission`) en un método nuevo `callCeo(...)`: si el proveedor configurado es NVIDIA y el presupuesto diario (`AiBudgetService`, `AtomicInteger` con reset por fecha calendario vía `Clock` inyectado, sin persistencia entre restarts — mismo criterio que `Agent.status`) ya se agotó, o si la llamada lanza excepción, o si la respuesta viene vacía **y sin `tool_calls`** (un `content` vacío CON `tool_calls` es un turno de herramienta normal, no un fallo), se reintenta contra `OllamaLlmProvider` y se publica `EMPRESA_CEO_PROVIDER_FALLBACK` (`data: {operation, reason}`, `reason` ∈ `RATE_LIMIT_OR_ERROR|BUDGET_EXHAUSTED`) — nunca gatea el camino Ollama-como-principal, que sigue exactamente igual que antes de esta ronda.

**Normalización de formato en ambos sentidos** (la pieza que hace posible el tool-calling de NVIDIA, ya que `CeoService` es deliberadamente agnóstico de proveedor): NVIDIA devuelve `function.arguments` como string JSON serializado (Ollama lo entrega ya decodificado) — `NvidiaNimLlmProvider.parseResponse` lo decodifica al recibir. En sentido inverso, `CeoService.chat()` reconstruye un mensaje `assistant` con `tool_calls` (`arguments` como `Map`, pensado para Ollama) para el segundo turno — `normalizeOutgoingMessages` lo re-serializa a string antes de mandarlo a NVIDIA.

**6 hallazgos reales de la revisión final de rama (ninguno crítico), corregidos en una sola ronda de fix**:
1. **Round-trip de tool-calling con NVIDIA roto** (Importante): `parseResponse` descartaba `id`/`type` de cada tool call, y `CeoService` nunca incluía `tool_call_id` en el mensaje `role:"tool"` siguiente — ambos exigidos por la API OpenAI-compatible que implementa NVIDIA. Fallaba de forma segura (400 → excepción → fallback a Ollama con un `reason=RATE_LIMIT_OR_ERROR` engañoso), pero anulaba media feature. Fix, acotado enteramente dentro de `NvidiaNimLlmProvider` (`CeoService` no se tocó): `parseResponse` preserva `id`/`type`; `normalizeOutgoingMessages` sintetiza un `id` (+`type:"function"`) en el mensaje `assistant` saliente cuando falta, y lo propaga como `tool_call_id` al mensaje `role:"tool"` inmediatamente siguiente (esta app siempre manda un solo tool call por turno, confirmado leyendo `chat()`/`executeAgentTask`). Bundle con esto: `chat(...)` ahora envuelve la llamada de red + el parseo en un try/catch que loguea `NVIDIA_ERROR` antes de relanzar (mismo patrón que `OllamaLlmProvider`).
2. **Riesgo de bean ambiguo en Spring** (Importante): `CeoService`'s `OllamaLlmProvider ollamaFallbackProvider` no tenía `@Qualifier`, y con `llm.ceo-provider=ollama` (default) los beans `ollamaLlmProvider`/`ceoProvider` resuelven a la misma instancia — riesgo teórico de `NoUniqueBeanDefinitionException` al arrancar, dependiente de un detalle de timing interno del contenedor, no del código. Fix: `@Qualifier("ollamaLlmProvider")` explícito.
3. **El chequeo de "respuesta vacía" empeoraba el camino default (Ollama, hoy 100% de producción)** (Importante): el throw-si-vacío se aplicaba sin condición, convirtiendo una rara respuesta vacía de Ollama en un HTTP 500 (`chat`, turno ni siquiera se registra) o en una misión `FAILED` completa (`executeMission`, descartando el trabajo real de los 5 agentes) — contradice directamente el principio ya documentado "Agent failure ≠ Mission failure". Fix: el throw ahora solo aplica cuando el proveedor configurado es NVIDIA; en Ollama, una respuesta vacía se devuelve tal cual (con un `log.warn`), sin excepción ni intento de fallback.
4. **Sin test para el caso real de NVIDIA** (Importante): ningún test cubría "content vacío CON `tool_calls`" (la forma real de todo turno de herramienta de NVIDIA) como éxito, no fallo — una simplificación ingenua de la condición habría roto todo el tool-calling de NVIDIA dejando la suite en verde. Fix: test nuevo cubriendo exactamente ese caso.
5. **Pérdida de observabilidad del camino exitoso del CEO** (Importante): las llamadas del CEO dejaron de loguear nada en éxito (antes, `OLLAMA_METRICS` completo), invalidando en silencio la convención de verificación ya establecida en este mismo archivo de grepear la *ausencia* de `CEO_CHAT` como prueba de que un camino determinista no tocó el LLM — ese grep ahora da "limpio" incluso cuando el CEO sí fue llamado. Fix mínimo: `log.info("CEO_PROVIDER_CALL operation={} provider={}", ...)` en el camino exitoso de `callCeo`.
6. **`EMPRESA_CEO_PROVIDER_FALLBACK` faltaba en `docs/EVENTS.md`** (Importante): agregado siguiendo el estilo existente del catálogo.

Además, bundle de bajo costo en la misma ronda: `AiBudgetServiceTest` tenía un test con nombre engañoso que no probaba nada del límite ≤ 0 — renombrado y agregado el caso real (`NVIDIA_DAILY_CALL_LIMIT=0` es, de hecho, un kill-switch inmediato hacia Ollama, antes indocumentado).

**Hallazgos menores parqueados con ruling, no corregidos** (sin ningún riesgo funcional actual): el `instanceof NvidiaNimLlmProvider` para gatear el presupuesto es pragmático con 2 proveedores pero acopla `CeoService` a una implementación concreta — se revisaría si aparece un tercer proveedor o un decorador/proxy; `recordCall()` solo cuenta llamadas exitosas, así que un NVIDIA persistentemente caído sigue intentándose en cada llamada del CEO sin que el presupuesto lo frene (aceptable: es un tope de cortesía, no un control de gasto real, y el fallback a nivel app ya protege la respuesta); `normalizeOutgoingMessages` descarta en silencio (en vez de pasar tal cual) un ítem de `tool_calls` que no sea `Map` (hoy nunca ocurre); `parseResponse` asume que `arguments` siempre es un string (documentado así en el contrato de NVIDIA); `AiBudgetService` combina `synchronized` + `AtomicInteger` + `volatile`, redundante pero inofensivo; `EMPRESA_CEO_PROVIDER_FALLBACK reason=BUDGET_EXHAUSTED` se publica en cada llamada mientras el presupuesto siga agotado, no solo en la transición (ruido aceptable de auditoría, mismo criterio que el resto de eventos Kafka del proyecto).

**Verificado en vivo, los 4 escenarios del plan** (Docker real, `mvn test` 235/235; contenedores de prueba efímeros vía `docker run` para no tocar `.env`/`docker-compose.yml` del despliegue real):
1. **Default, sin NVIDIA**: arranca sano (sin `NoUniqueBeanDefinitionException`, confirmando en vivo que el riesgo del hallazgo #2 no se materializa), un chat real respondió vía `OllamaLlmProvider` (`CEO_PROVIDER_CALL provider=OllamaLlmProvider` en el log), cero eventos de fallback.
2. **NVIDIA sano, con una API key real** (recuperada de un spike anterior de esta misma sesión, confirmada todavía activa contra el endpoint real antes de usarla): un chat general respondió en ~2s vía `NvidiaNimLlmProvider` real, sin fallback. Más importante — **el round-trip de tool-calling que el hallazgo #1 debía arreglar se probó de punta a punta con éxito real**: la pregunta "contame con tus propias palabras cómo le está yendo a Forjai" (deliberadamente sin ningún keyword determinista) disparó `CEO_CHAT_TOOL_CALL topic=COMPANY_STATUS` y la respuesta narrativa del CEO citó las cifras reales exactas (US$50.00 capital, 0 agentes trabajando/6 inactivos, 0 de todo lo demás) sin ningún `NVIDIA_ERROR` ni fallback — confirma que `id`/`type`/`tool_call_id` quedaron bien resueltos en el segundo turno.
3. **Fallback real** (mismo proveedor NVIDIA, API key inválida a propósito): el chat general igual respondió (vía Ollama), con `NVIDIA_ERROR operation=CEO_CHAT model=openai/gpt-oss-20b` logueado **sin exponer la clave** (confirmado grepeando el log) seguido de `CEO_PROVIDER_FALLBACK operation=CEO_CHAT reason=RATE_LIMIT_OR_ERROR`.
4. **Presupuesto agotado** (`NVIDIA_DAILY_CALL_LIMIT=0`, misma clave inválida): `CEO_PROVIDER_FALLBACK reason=BUDGET_EXHAUSTED` sin ningún `NVIDIA_ERROR` en el log — confirma que el gate de presupuesto corre antes de siquiera intentar la red.

**Fuera de alcance de esta ronda, a propósito** (ver el spec): presupuesto persistido/por misión/por agente (contador global simple es suficiente hoy); que los agentes delegados también puedan usar NVIDIA (diseño aprobado es "CEO potente, workers locales"); auto-hospedar un modelo NVIDIA localmente (requiere hardware no disponible hoy).

### Memoria conversacional como grafo histórico por día (Sub-proyecto C de "Company Chat completo")

**Contexto**: el usuario pidió evaluar si la conversación con el CEO debería modelarse como un grafo real en Neo4j — hoy, aunque ya vivía dentro de Neo4j (`ConversationMemoryService`), estructuralmente era solo una lista enlazada plana (`Conversation`→`Message` directo) más un puntero mutable de "foco" que se pisaba en cada consulta nueva, sin ningún vínculo hacia las entidades reales de las que hablaba cada mensaje. Alcance acordado con el usuario en brainstorming (3 preguntas explícitas): solo chat con el CEO (no con agentes individuales); agrupación por día calendario, sin heurística de tema/inactividad; y tres capacidades nuevas — preguntar por un día pasado, vincular cada día a las entidades reales discutidas, y una forma de memoria más allá de la ventana fija de 20 mensajes — resuelta como recuperación explícita bajo demanda (no subir el límite fijo, no resúmenes automáticos vía LLM).

**Diseño**: nodo nuevo `Chat {date}` entre `Conversation` y `Message` (uno por día calendario, `MERGE` por fecha), con edges `MENTIONS` hacia las entidades reales (`Mission`/`Customer`) discutidas ese día. El foco actual (`lastMentionedType`/`lastMentionedIds`) no se tocó — sigue siendo el único mecanismo para resolver pronombres del turno actual; los edges `MENTIONS` son un rastro histórico *adicional*. Migración idempotente (`ConversationMemoryService.migrateMessagesToChats`, corre en cada arranque vía `CompanyMemoryInitializer`) reengancha cualquier `Message` viejo bajo el `Chat` de su fecha real. Dos consultas nuevas, mismo patrón ya establecido de `MISSION_DETAILS`/`OPPORTUNITY_DETAILS`: `CHAT_HISTORY` ("¿qué hablamos el [día]?", resuelve "hoy"/"ayer"/fecha explícita `DD/MM[/YYYY]` vía un `Clock` inyectado — reusa el bean `Clock` ya existente en `CoreConfig` desde la ronda de NVIDIA) y `MENTIONED_DATES` ("¿en qué días hablamos de MISSION-X?"). Cada call-site que ya llama `setLastMentioned` (6 en `CompanyTools` + el arranque de misión libre en `ChatIntentRouter`) gana además una llamada a `recordChatMention`, reusando la misma detección existente.

**Bug real encontrado durante la implementación de la Task 3 (no una desviación del implementador, un hueco del plan)**: el código literal para `resolveChatHistoryQuery` colisionaba con un test ya existente — "Aprueba la misión de la que hablamos ayer." (un mensaje de decisión sin `MISSION-<id>` explícito) contiene "hablamos"+"ayer" y quedaba interceptado como consulta de historial en vez de caer al chat general. Mismo patrón de colisión de keywords ya documentado 4 veces en este archivo (`\bprueba`/`aprueba`, `decision`/`decisiones`, `contact`/`contactar`). Fix: exigir que el mensaje contenga un `"?"` literal — verificado independientemente dos veces (por el reviewer de la tarea y por el reviewer final) como la corrección correcta y proporcionada, sin alternativa mejor (excluir verbos de decisión es más frágil, ya que el chat también soporta comandos/instrucciones de formato libre sin una lista acotada de verbos).

**7 hallazgos reales de la revisión final de rama (2 Importantes, 5 Menores accionables; ninguno Crítico), corregidos en una sola ronda de fix**:
1. **`getChatHistory` sin límite y autoamplificándose exponencialmente** (Importante): `ChatIntentRouter.route()` graba incondicionalmente cada respuesta (incluida la propia respuesta de `CHAT_HISTORY`) de vuelta en el `Chat` del día — preguntar "¿qué hablamos hoy?" repetidamente duplicaba aproximadamente el transcript en cada vuelta, reintroduciendo el mismo problema de payload gigante ya documentado en este archivo (69 KB, el modelo subcontó "9 de 25"). Fix: `CHAT_HISTORY_MAX_MESSAGES=30`/`CHAT_HISTORY_MESSAGE_MAX_CHARS=200`, mismo patrón de truncado que ya usa `getRecentDecisions`.
2. **Faltaba `recordChatMention` en `ChatIntentRouter.handleFreeMissionStart`** (Importante): el spec lo nombraba explícitamente como call-site requerido, pero el plan lo redujo a "los 6 puntos de `CompanyTools`" sin justificar el recorte. Bug concreto: arrancar una misión por chat libre y preguntar de inmediato "¿en qué días hablamos de esa misión?" respondía "no encontré menciones" sobre el día en que nació en ese mismo chat. Fix: una línea, `recordChatMention("MISSION", List.of(missionId))` junto al `setLastMentioned` existente.
3. **`migrateMessagesToChats` sin guarda contra `createdAt` nulo** (Menor): mismo patrón defensivo ya establecido la ronda anterior para `MissionMemoryService.recentDecisions` — agregado `WHERE m.createdAt IS NOT NULL`.
4. **Inconsistencia UTC vs. zona local en el bucketing por día** (Menor, documentado no corregido): `recordMessage` agrupa por la zona local del `Clock` inyectado, la migración agrupa por UTC (extraído del `Instant` crudo) — sin impacto hoy (ningún `TZ` configurado en el Docker real), documentado como límite conocido, mismo criterio que el DNS rebinding de `WebPageFetcher`.
5. **Keywords por substring crudo en vez de `Pattern` con boundary** (Menor): 5ª instancia del mismo patrón de bug ya mencionado arriba — `"dias"` matcheaba dentro de "guardias". Fix: `Pattern`s `\b`-acotados (`TALKS_ABOUT_HISTORY`, `DIAS_WORD`, `MENTIONED_KEYWORD`).
6. **Sin test de regresión para fecha explícita inválida** (Menor): `31/02` ya se manejaba bien en el código (excepción capturada, cae al chat general, nunca un 500), pero sin ningún test que lo fijara — agregado.
7. **Framing excesivamente confiado del gate `"?"`** (Menor, documentado): el reviewer final encontró un ejemplo concreto de frase compuesta ("Aprueba la misión de la que hablamos ayer. ¿Podés confirmar?") donde el gate igual falla de forma segura pero no es "inofensivo" del todo — Javadoc corregido para reflejarlo, sin cambio de lógica.
8. **Cobertura de test incompleta para `recordChatMention`** (Menor): solo 2 de 6 call-sites de `CompanyTools` tenían test directo — agregados los 4 restantes.

### Contacto real por email a prospectos (Sub-proyecto D de "Company Chat completo", cierre de la iniciativa)

**Contexto**: hasta esta ronda, "contactalo" (ver "Chat con prospectos reales por misión" más arriba) era una respuesta puramente informativa — nunca mandaba nada real. El fundador pidió cerrar esa brecha: que el comando realmente le escriba a un prospecto real por email. Alcance acordado con el usuario en brainstorming (3 preguntas explícitas): el agente busca y reporta el email de contacto (nunca lo fabrica); el envío es directo, sin paso de confirmación intermedio; el contenido es una plantilla determinista, nunca redactada por el CEO/LLM. El usuario aclaró además, durante el brainstorming, que el correo general/de ventas de una empresa (`info@`/`ventas@`) es un dato de contacto tan válido como el de una persona puntual — ni el prompt del agente ni el código distinguen entre ambos.

Una v2 del spec, pegada por el usuario a mitad de la ronda, agregaba Governance (`mission.contactAllowed`), secret manager para credenciales, `providerMessageId`, rate limiting y una Activity Feed — verificado contra el código real antes de aceptar nada: `Governance` no existe en ningún lado del proyecto, "secretos solo en secret manager" contradice la decisión ya aceptada de guardar `mailPassword` en Neo4j (ver "Alertas por correo" más arriba), y `providerMessageId` no es viable con SMTP genérico vía `JavaMailSenderImpl` (`send()` es `void`, ese dato es de proveedores tipo API como SendGrid). El usuario, con las tres infactibilidades ya señaladas, eligió recortar a lo esencial: mantener de la v2 solo `ContactAttempt` como entidad real de primera clase y el CAS de idempotencia, descartar el resto como "fuera de alcance, no descartado".

**Diseño**: `CustomerCandidate`/`LeadResponse` ganan `contactEmail`/`contactEmailSource` (ambos opcionales, pero `contactEmailSource` obligatorio si `contactEmail` viene no vacío — `AgentResultValidator` lo exige). `ContactAttempt` es un nodo real (`(:Customer)-[:HAS_CONTACT_ATTEMPT]->(:ContactAttempt {id, channel:'EMAIL', destination, subject, status, initiatedAt, sentAt, errorMessage})`) — no solo un flag de status, así queda una auditoría real de cada intento con o sin éxito. `OpportunityMemoryService.claimForContact` hace el CAS (`LEAD`→`CONTACT_IN_PROGRESS`) que evita que dos "contactalo" casi simultáneos disparen dos envíos. `AlertMailService.sendToExternal` (nueva, hermana de `send` — la alerta interna al fundador, que queda completamente intacta) manda a un destinatario arbitrario y sí reporta éxito/fallo real (a diferencia de `send`, que nunca lanza y no tiene esa necesidad). `ProspectOutreachEmailTemplate` arma el contenido determinista. `CompanyTools.contactProspect` es el único punto de orquestación con el efecto externo real: guardia de email vacío → CAS → registra el intento → envía → marca `SENT`/`FAILED` + publica `EMPRESA_PROSPECT_CONTACTED`/`EMPRESA_PROSPECT_CONTACT_FAILED`.

**La revisión final de rama encontró 2 hallazgos Críticos, 4 Importantes y 4 Menores, corregidos en un fix wave + una corrección puntual adicional tras la re-revisión** (proceso completo, no solo revisión por tarea — esta es la primera feature del proyecto con un efecto externo real e irreversible hacia un tercero, así que se pidió especial atención a race conditions y fugas de datos):

1. **(Crítico) El gate de "contactalo" también disparaba un envío real ante preguntas puramente informativas.** `formatCustomerReferenceAnswer` llamaba a `contactProspect` incondicionalmente cada vez que el mensaje matcheaba el patrón amplio de entrada (`CONTACT_REFERENCE = \bcontacta(lo|la|me|los|las)?\b|\bcontacto de\b`) — así que "¿cuál es el contacto de Panadería El Sol?" o "contactame cuando termines" (el fundador hablando de sí mismo, no ordenando contactar al prospecto) mandaban un correo real a un tercero para una simple pregunta. Fix: `CONTACT_COMMAND` (`\bcontacta(lo|la|los|las)\b`, sin "me"), subconjunto estricto del gate de entrada, es ahora el único patrón que autoriza el envío real; toda otra forma reconocida por `CONTACT_REFERENCE` es puramente informativa — muestra el prospecto real y sugiere decir "contactalo" para efectivamente mandarlo.
2. **(Crítico) El javadoc de `handleCustomerReference` afirmaba "esta ronda es puramente informativa" cuando en realidad ya dispara un envío real** — documentación que, de no corregirse, habría invitado a un cambio futuro a reensanchar el gate sin darse cuenta del riesgo. Corregido apuntando a `formatCustomerReferenceAnswer`/`CONTACT_COMMAND` como la única fuente de verdad sobre cuándo se manda algo de verdad — este fue el único hallazgo que sobrevivió al primer fix wave (el brief nunca instruyó tocar explícitamente este bloque viejo) y se cerró en una segunda corrección puntual tras la re-revisión.
3. **(Importante) El CAS de `claimForContact` no era realmente atómico en Neo4j.** El idioma original (`MATCH {status:'LEAD'} SET status='CONTACT_IN_PROGRESS'`, el mismo que ya usan `markConverted`/`discardLead`) evalúa el predicado contra el estado comiteado *antes* de tomar el lock de escritura (Neo4j es read-committed, el lock se toma recién en el `SET`) — dos transacciones solapadas podían leer `LEAD` antes de que cualquiera comiteara, y ambas terminaban escribiendo: doble envío real. Fix con el idioma estándar "lock-then-check": `SET c.contactLock=$now` incondicional primero (fuerza el lock de escritura de inmediato sobre una propiedad dedicada, no `updatedAt`, para que un claim fallido nunca parezca un cambio de estado real) → `WITH c WHERE c.status='LEAD'` (re-evalúa ya bajo el lock, viendo el estado real y comiteado) → `SET` real. Cierra genuinamente la ventana de lost-update — razonado independientemente dos veces (revisión final + re-revisión del fix) contra el modelo de locking real de Neo4j, no solo confiado por diseño.
4. **(Importante) El email de outreach reutilizaba el pie de página y el tema visual de una alerta interna del sistema.** `AlertEmailTemplate.html` tenía el footer "Alerta automática — Command Center" hardcodeado — un desconocido recibiendo un correo de prospección real lo veía presentado como una alerta de sistema. Fix: overload de 4 argumentos con footer configurable; `sendToExternal` usa "Mensaje enviado por Forjai — no es una alerta automática"; `send` (la alerta interna real) sigue exactamente igual, sin tocar.
5. **(Importante) El cuerpo del correo citaba textualmente la descripción interna que el agente escribió *sobre* el prospecto** (`candidate.description()`, redactada para revisión interna, no para que la lea el prospecto) — con datos reales de agentes podía leerse gramaticalmente roto o como una valoración poco favorable del propio negocio del destinatario. Fix: se dejó de interpolar `description()`; el asunto ahora sí usa el nombre real del candidato (antes lo ignoraba pese a recibirlo como parámetro).
6. **(Importante) Una excepción en el registro posterior al envío (Neo4j/Kafka) podía ocultar que el correo sí salió, y devolver un 500 crudo** (el proyecto no tiene `@ControllerAdvice`, y la excepción cortaría antes de que `route()` grabara el turno). Fix: los dos bloques de bookkeeping posteriores al resultado del envío (`markContactSent`+publish, `markContactFailed`+publish) quedan en try/catch que loguea y continúa — el mensaje real de éxito/fallo siempre se devuelve al fundador, pase lo que pase con el registro.
7. **(Menor) `recordContactAttempt` sin guarda de existencia** — devolvía un `attemptId` fantasma si el `MATCH` no encontraba el lead. Fix: lanza si el `CREATE` no se ejecutó de verdad.
8. **(Menor) `ContactAttempt` sin constraint de unicidad en Neo4j**, a diferencia de toda otra entidad real del grafo. Agregado junto a `evidence_id`.
9. **(Menor) Un prospecto `CONTACTADO` desaparecía de los conteos de "dame un status"** (solo contaba `customers`/`prospects`, nunca `CONTACTADO`). Fix: tercer conteo, línea nueva "Contactados: N." en `getCompanyStatus`.

`mvn test`: 268/268 (fin de las 4 tareas) → 275/275 (fin del fix wave, +7 tests nuevos) → 275/275 (fix puntual del javadoc, sin cambio de tests).

**Verificado en vivo de punta a punta** (Docker reconstruido con el código final, Neo4j real — encontrada en volumen limpio, sin misiones/clientes previos de esta sesión, así que se sembró todo desde cero): un `Customer{status:'LEAD'}` real con `contactEmail=dapine@gmail.com` (dirección propia del fundador, para no mandarle nada a un tercero real durante la prueba, tal como especificaba el plan) enlazado a una `Opportunity` de una misión `TEST` sembrada — "contactalo a [nombre]" mandó el correo real (confirmado por la ausencia de `WARN` en `AlertMailService` y por el `ContactAttempt{status:'SENT'}` real en Neo4j), el `Customer` pasó a `CONTACTADO`. Repetir "contactalo" de inmediato sobre el mismo prospecto respondió el mensaje determinista de "ya tiene un contacto en progreso o ya fue contactado" **sin** un segundo `ContactAttempt` (confirmado con Cypher: 1 solo intento). **La prueba específica del fix Crítico #1**: preguntar "¿cuál es el contacto de [otro prospecto]?" sobre un segundo `Customer{status:'LEAD'}` sembrado devolvió la ficha del prospecto invitando a decir "contactalo" — **sin** tocar Neo4j (confirmado: `status` seguía en `LEAD`, 0 `ContactAttempt`) — la pregunta que antes del fix habría mandado un correo real a un tercero. Fallo forzado real contra ese mismo segundo prospecto (contraseña del sistema temporalmente inválida, respaldada y restaurada vía Neo4j directo para nunca perder la App Password real): `"Intenté enviar el correo, pero no se pudo (Authentication failed)"`, el `Customer` **volvió a `LEAD`** (no quedó atascado en `CONTACT_IN_PROGRESS`) con un `ContactAttempt{status:'FAILED', errorMessage:'Authentication failed'}` real; restaurada la contraseña real, "contactalo" sobre el mismo prospecto reintentó con éxito. Los 3 eventos reales de Kafka (`EMPRESA_EVENTS`) confirmados: `EMPRESA_PROSPECT_CONTACTED`/`EMPRESA_PROSPECT_CONTACT_FAILED`/`EMPRESA_PROSPECT_CONTACTED` con los `leadId`/`attemptId`/`recipientEmail`/`reason` reales y correctos, sin ningún fragmento de credencial expuesto. Datos de prueba borrados de Neo4j al terminar.

**Límite conocido, no resuelto** (mismo criterio que el DNS rebinding de `WebPageFetcher`/`Agent.status` tras un restart): si el proceso se cae entre el CAS (`claimForContact`) y el `mark*` correspondiente, el `Customer` queda atascado en `CONTACT_IN_PROGRESS` sin ningún endpoint ni comando de chat para revertirlo — recuperable solo a mano por Cypher, igual que un lead `CONVERTIDO` huérfano. Tampoco hay tracking de respuestas: el correo invita a responder al buzón `systemEmail`, que nadie monitorea por proceso — el fundador tiene que revisarlo a mano.

**Fuera de alcance de esta ronda, a propósito** (recortado explícitamente de la v2 pegada por el usuario, ver arriba): Governance (`mission.contactAllowed`), secret manager para `mailPassword` (contradice la decisión ya aceptada de guardarlo en Neo4j), `providerMessageId` (no viable con SMTP genérico), rate limiting, métricas dedicadas, pipeline de status extendido, Activity Feed.

Con esta ronda se completan las 5 sub-iniciativas (A, B, E, C, D) de "Company Chat completo" — no hay más sub-proyectos en cola de esta iniciativa salvo pedido nuevo del fundador.
